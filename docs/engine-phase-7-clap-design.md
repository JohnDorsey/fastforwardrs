# Phase 7, piece 7.8: CLAP sound plugins (design, before the code)

Written 2026-10-20, at your word ("start the CLAP design now"), after you heard 7.6 in the preview ("sounds good"; the export is not tried yet). It is the design that
[the design of phase 7](engine-phase-7-design.md), section 7, said would be written after 7.6, "so that it is made from what LADSPA taught". Nothing is built. It follows
the form of the other designs: **what I checked, what CLAP asks of a host, decisions (C1 to C14), pieces, tests, risks, and the questions I need answered**.

**[V]** means I read it in the headers of CLAP today (`free-audio/clap`, `main`, version **1.2.10** in `version.h`; the files are named where they matter). **[B]** means I believe it
from experience of how plugins behave, or from reasoning, and it has not been run. **[P]** is a proposal of mine that stands unless you object.

## 1. Why CLAP, and what it is for this program

LADSPA binaries are almost only found on Linux; **CLAP is the format that users of all three systems have** (AU-02, Q-27: "LADSPA first, then CLAP"). The graph, the trust model, the scan in a
child process, the registry, the menu (a smaller menu for *CLAP* appears by itself: `source_of` already says `clap` for a key that begins `clap:`), the project file and the folder
questions are built for the second format already. What is new is **a host for the C interface of CLAP**, and four things LADSPA did not have: plugins with **their own parameter ids
and flags**, **events with a sample offset**, a **latency** the host should compensate, and **a main thread and an audio thread** that the plugin is told apart by.

## 2. What CLAP asks of a host [V unless said]

* **The entry.** A `.clap` file (a plain library on Windows and Linux; **a bundle, a folder, on macOS**) exports one symbol, `clap_entry`, a `clap_plugin_entry_t { clap_version, init(path), deinit(), get_factory(id) }`
  (`entry.h`). `init` must be called first, with the path of the file (of the bundle on macOS), may not run at the same time as any other CLAP symbol, and must be fast and do nothing visible;
  `deinit` frees what `init` made. `get_factory` is thread-safe. If `init` returns false, nothing else may be called.
* **The factory.** `get_factory("clap.plugin-factory")` is a `clap_plugin_factory_t { get_plugin_count, get_plugin_descriptor(index), create_plugin(host, id) }` (`factory/plugin-factory.h`). Everything in it is
  thread-safe; the descriptor lives until `deinit`; **the `clap_host_t` given to `create_plugin` must stay valid until after `plugin->destroy`**; the plugin may not use the host inside `create_plugin`.
* **The descriptor** is `{ clap_version, id, name, vendor, url, manual_url, support_url, version, description, features }` (`plugin.h`); `id` (a reverse-domain string, **globally unique**) and `name` are mandatory; `features` is a
  null-terminated list of words (`audio-effect`, `instrument`, `stereo`...) [V that it exists; the words are in `plugin-features.h`, which I did not read: B].
* **The plugin** is `{ desc, plugin_data, init, destroy, activate(rate, min_frames, max_frames), deactivate, start_processing, stop_processing, reset, process, get_extension, on_main_thread }`.
  **Threads are part of the contract:** `init`, `activate`, `deactivate`, `destroy` and `on_main_thread` are for **the main thread**; `start_processing`, `process`, `stop_processing` and `reset` are for **the audio thread**;
  `get_extension` is thread-safe but not before `init`. The order is *create, init, activate, start_processing, process (many), stop_processing, deactivate, destroy*; the pointers in `process` are valid only for the call;
  **`reset` clears buffers and voices and keeps the parameter values**.
* **`process`** takes `clap_process_t { steady_time (-1 if unknown, else it grows by at least frames_count), frames_count, transport (null for a host with no transport), audio_inputs, audio_outputs, the counts, in_events, out_events }` and returns
  `ERROR` (discard the output), `CONTINUE`, `CONTINUE_IF_NOT_QUIET`, `TAIL` or `SLEEP`. An audio buffer is `{ data32, data64, channel_count, latency, constant_mask }`: **one of the two pointers is set**; `constant_mask` is only a hint that a channel is one value all through.
* **Ports** are the extension `clap.audio-ports`: `count(is_input)` and `get(index, is_input, info)` with `{ id, name, flags (main, supports 64 bits, prefers 64 bits, requires common sample size), channel_count, port_type ("mono", "stereo", null for anything), in_place_pair }`. **The main port is
  at index 0**; 32 bits is required of both sides. The port list may change only while the plugin is deactivated.
* **Parameters** are the extension `clap.params`: `count`, `get_info(index)` giving `{ id (stable: never changes), flags, cookie, name, module (a path with "/"), min_value, max_value, default_value }`, `get_value(id)`, `value_to_text`, `text_to_value`, `flush`.
  The flags that matter to us: *stepped* (an integer; the double is truncated), *periodic*, *hidden*, *readonly*, **bypass** (stepped, at most one, 0 off and 1 on), *automatable*, *modulatable*, *requires process*, ***enum*** (stepped, and every value from min to max has a text).
  **A change is an event, `CLAP_EVENT_PARAM_VALUE`, with `time`, the sample offset in the block** (`events.h`: `{ header{size,time,space_id,type,flags}, param_id, cookie, note_id, port_index, channel, key, value }`, the wildcards are -1);
  input events must be sorted by time. Changes are given in `process`, or in `flush` when there is no audio: not both.
* **Latency** (`clap.latency`): `get()` in samples, **only allowed to change in `activate`** (otherwise the plugin asks `request_restart`). **Tail** (`clap.tail`): `get()` in samples, INT32_MAX or more is infinite.
* **State** (`clap.state`): `save(ostream)` and `load(istream)` on the main thread, with streams that may move fewer bytes than asked (loop until done). This is the only way to keep what a plugin knows that is not a parameter.
* **The host** is a `clap_host_t { clap_version, host_data, name, vendor, url, version, get_extension, request_restart, request_process, request_callback }`: all four callbacks are thread-safe; **`request_callback` asks for `on_main_thread` to be called, within about 33 ms**.
  The host should offer `clap.thread-check` (`is_main_thread`, `is_audio_thread`) and may offer `clap.params` (`rescan`, `clear`, `request_flush`), `clap.latency` (`changed`), `clap.tail`, `clap.state` (`mark_dirty`), `clap.audio-ports` (`rescan`).
* **Where CLAP files are:** Linux `~/.clap` and `/usr/lib/clap`; Windows `%COMMONPROGRAMFILES%\CLAP` and `%LOCALAPPDATA%\Programs\Common\CLAP`; macOS `/Library/Audio/Plug-Ins/CLAP` and `~/Library/Audio/Plug-Ins/CLAP`; and the variable `CLAP_PATH`
  (a list in the way of the system), searched recursively for names that end in `.clap`.
* The headers are MIT-licensed [B: the header files say so at their top; I did not read the notice]; hosting in a GPL-3.0 program is fine (LG-04).

## 3. Decisions

| # | decision | why |
|---|---|---|
| **C1** | **The `clack-host` crate** (0.2.0, MIT OR Apache-2.0, Rust 1.85, built on `clap-sys`; **your decision, 2026-10-20**), with `clack-extensions` for the extensions, behind **a small crate of our own, `crates/clap-host`**, that is the only place that names `clack`: it gives the program what `ladspa-host` gives (a library that can be loaded and described, an instance that can be run), so that the rest of the editor does not depend on `clack`'s types and a change of crate would be a change of one crate. Our crate has `#![forbid(unsafe_code)]` except the one call that loads a file (`PluginEntry::load` is `unsafe` because loading runs the code of the library), which has its reason and is counted by an audit test as the LADSPA ones are. The test plugins are written with `clack-plugin` (so they share `clap-sys` with the host: **the independence that the LADSPA test plugin had from the host's own definitions is lost; the layout of the structures is `clap-sys`'s, generated from the headers, and the contract (threads, order, lifetimes) is still tested by a plugin that enforces it**). | Fewer than a thousand lines of definitions and wrappers that someone else keeps in step with the headers, with a design (main thread / audio thread, `!Send` where the contract says) that already matches C8. The cost is a young dependency and `clack`'s idea of an instance; the crate in between is what makes that cost small. |
| **C2** | **One scan program for both formats.** `fastforwardrs-plugin-scan <file>` looks at the ending: `.clap` is CLAP, as before the others are LADSPA; the answer says which. The cache, the 5 s limit, the breadcrumb and the failure kinds are shared. | One place that decides what is a failed library (DS-04), one cache file, one window. |
| **C3** | The scan **creates every plugin, initialises it, activates it at 48000 Hz for 1 to 512 frames, starts processing, runs one block of silence, stops, deactivates and destroys it**, and reports: id, name, vendor, version, description, features, the audio ports (counts, channel counts, types, flags), every parameter (id, name, module, min, max, default, flags and, for an enum, the texts), whether it has `latency`, `tail` and `state`, and the latency and tail it reports. | As for LADSPA (7.4): a plugin that crashes in its constructor must crash the scan, not the editor. |
| **C4** | **The key is `clap:<id>`** (the id is a reverse-domain string that is unique in the world: no file stem, as ID-01 wanted and as LADSPA's `ladspa:<stem>:<label>` could not do), version 1.0 with the plugin's own version in the description. **The id of a value is `param<number>`** (the number is the parameter's `id`, which CLAP says never changes); the name is only a label, so a plugin that renames a parameter is still the same plugin. A plugin is *the plugin that was scanned* if its id is the same and the parameter ids it has include those the snapshot has. | The names of the saved effects survive a plugin update; two copies of one plugin in two folders are one effect, and the first folder wins (as now). |
| **C5** | **What is an effect:** a plugin with an audio input and an audio output on its main ports, whose main ports are mono or stereo (or a port with no type and 1 or 2 channels). Extra ports (a side chain, a second output) are given **silence** as input and ignored as output. A plugin with no audio input (an instrument, a generator) is listed as not used with the reason, as for LADSPA. Surround, ambisonic and more than two channels: not used, with the reason. | It is the same four layouts as 7.6, and the host never has more than two channels. |
| **C6** | **Parameters become values:** a number with a range (min to max) where the plugin has one; **stepped becomes a whole number; enum becomes a choice** (the options are the texts from `value_to_text`, the id of an option is the number); **a bypass parameter becomes a switch** (not the bypass of the effect: that is the program's, which passes the sound through whatever the plugin does); **hidden and read-only parameters are not values**; periodic is a number with a range like any other. The default is `default_value`. A parameter with an infinite range is not a value (CLAP says both ends are finite, so this should not happen: it is refused as a descriptor that cannot be used). | The same rule as the control inputs of LADSPA, with the flags CLAP has. |
| **C7** | **Sample-accurate values are events.** A value that has keyframes is looked at every 32 samples (as for LADSPA, so that the two formats are held to the same arithmetic); where it has changed, **one `CLAP_EVENT_PARAM_VALUE` with `time` the offset of those 32 samples in the block** is put in the input events of that `process`. A value that has none is sent once, at sample 0 of the first block, and again after a reset. Events are sorted by time (they are made in order). No block is split. The values are kept to the range, as now. | CLAP is built for this (a better fit for G11 than LADSPA); it costs less than splitting blocks, and it does not depend on the plugin being fast to start. |
| **C8** | **The plugin's threads are kept as the contract says.** The host has **a thread of its own for the plugin's main-thread calls** (create, init, activate, deactivate, destroy, `on_main_thread`, state): the graph asks it and waits for the answer (this happens when a clip is about to be heard, ahead of the sound, never inside a block). `is_main_thread` is true on it only; `is_audio_thread` is true on the thread that calls `process` (the stream's, or the export's). `request_callback` queues an `on_main_thread` there; `request_restart` marks the instance to be deactivated and activated again at the next block boundary; `request_process` is ignored (we always process). Everything on the host side is thread-safe, as CLAP says. | A plugin may assert the thread it is called on. Treating the graph's thread as both main and audio would make an assertion pass that the contract forbids, and might hide a mistake until a plugin that checks it. **[B] confidence medium that this is worth its cost:** one more thread and a hand-over for each instance; the alternative (the creating thread is "main" for that instance) is simpler and I think would work for most plugins. |
| **C9** | **Latency is compensated (AU-06).** The latency is read at `activate` (it cannot change after), and the graph is told it as a number for each insertion. For a clip whose effects have a latency L (the sum): the feed is read **L samples ahead** of the clip's position (silence after its end) and the first L samples that come out of the chain are dropped, so that the sound is where the picture is. The same for LADSPA, whose latency is 0. A plugin that asks `request_restart` because its latency changed is restarted at the next block, and the sound near it may click once (said in a note). | Without it a plugin of 2048 samples of look-ahead (a limiter) is heard 43 ms late: AU-06 is a should, and the feed of a clip is the one place it can be done. |
| **C10** | **Tail and pre-roll (AU-05).** After a seek the sound is made again, so a plugin begins cold (7.6). **I propose a pre-roll for plugins that remember: before a clip's first heard sample the chain is run for `min(tail, 2 s)` on sound read from before it** (the feed starts earlier; what comes out is dropped), when the clip has source before that point. `tail` is read from the plugin; an unknown tail is 0.5 s; an infinite one is 2 s. LADSPA has no way to say its tail, so **LADSPA plugins keep the behaviour of 7.6** (no pre-roll) unless you say otherwise. Built as its own piece, last. | A reverb that begins from silence at every seek is wrong for the first seconds of every play from the middle. The cost is source read twice and a longer start. |
| **C11** | **State is not kept in this release.** A plugin's own state (`clap.state`) matters when something changes it that is not a parameter: its window or a preset. **We host no window and no preset**, so the parameter values are the state, and they are the project's. The extension is *read* by the scan (the plugin says it has state) and the window says *this plugin keeps settings that only its own window can change, which cannot be shown here* where it has state and few or no exposed parameters. When a window or a preset exists, the bytes become a value of the effect (base64 in the file, with limits of 1 MiB for an effect and 16 MiB for a project). | Saving a blob that nothing can change is saving the default, and a state that the program cannot read is a file format that would have to be kept for ever. |
| **C12** | **No window for a plugin.** CLAP plugins are often judged by their window (`clap.gui`: embedded or floating, with a platform window handle). Hosting one is a piece of work of its own (a native window per system, in a program that draws with `egui`) and a separate question of safety. **Not here.** | See C11. |
| **C13** | **Trust is the folder model, unchanged.** A CLAP file is native code: the folder it is in is asked about once (*Run plugins from this folder?*), the command line refuses an unapproved folder, `--allow-plugins` allows all, the breadcrumb names the file, and an embedded plugin (`PluginLibraryKind::Clap`, a new kind in the project's list of libraries, with builds per platform; on macOS the build is a bundle and is embedded as an archive of it: **a decision I leave for the end**) gets the severe question. Folders looked in: the standard ones above, `CLAP_PATH`, and those a person adds (the window of where to look has one list for both formats). | One rule for native code; nothing new for a person to learn. |
| **C14** | **The registry grows one idea.** `InstalledPlugin` has `plugin_index` and `value_ports` (numbers that mean something only to LADSPA); they become **`address: PluginAddress`** (`Ladspa { index }` or `Clap { id }`) and `value_handles: Vec<u32>` (a port number for LADSPA, a parameter id for CLAP). `PluginEffect` is generalised over a small trait, **`PluginInstance`** (`set_value(handle, value, at_sample)`, `run(inputs, outputs, frames)`, `reset()`, `latency()`, `tail()`), that both hosts implement; the layouts, the 32-sample grid, the clamp, the silence for what is not a number or more than 1000 times full scale, the patience for a slow plugin, and the notes are written once. Project files do not change: the snapshot of an effect already has everything (`key`, `params` with ids and ranges, `category`, `domain`). **The file format stays 14**; an `enum` control is already a kind of control (`Choice`). | The least change that lets the second host in, and the 7.6 tests (to the sample, the seek, the slow plugin) become the tests of both. |

## 5. Tests

* **Reference first, again.** The arithmetic (the grid of 32, the offsets of events, the latency alignment) is written once in Rust on `f64` and the graph is held to it; the test plugin that writes the offsets of its events as sound makes "sample-accurate" a number a test reads.
* **The contract is tested by a plugin that enforces it.** The test plugin fails (and says so in its output) if it is called on the wrong thread, in the wrong state (`process` before `start_processing`, `activate` twice, `destroy` while active), with a host pointer that has been freed, or with events out of order.
* **The safety model is tested before anything loads**, as in 7.3: nothing new is built for it; the CLAP file goes through `load_library`.
* **Round trips**: a CLAP effect of a plugin that is not installed, one whose parameters changed (an id is gone), a bundle for another platform; saved, read, saved: byte for byte.
* **The real set** is a report, not a check, and runs on your computer: I do not know which CLAP plugins you have (question 3).
* **The mutation campaign** over every new module, aimed at the right test programs; the lesson of 7.6 applies: the aim takes one filter.

## 6. What this does not change, and what is not exact

* No window for a plugin (C12), no state (C11), no presets, no instruments, no note events, no modulation, no per-note or per-key parameters, no 64-bit audio, no surround, no `clap.remote-controls`, `clap.track-info` or the other extensions of the standard (the host says it does not have them).
* **Plugins run in the editor's process** (as in G4): a CLAP plugin that crashes ends the editor, and the breadcrumb says which file. CLAP plugins are in general more careful than LADSPA ones, and the scan runs each once [B].
* **A plugin that does not repeat itself** does not make the same sound in the preview and the export (as for 14 of the 211 LADSPA plugins): the plugin's own randomness.
* **Parameters with a scale that is not linear** (a frequency): CLAP does not say; the slider is linear in the plugin's own units [B: a frequency parameter in Hz from 20 to 20000 is a poor slider; `value_to_text` tells the units; a log slider for a range that spans more than three decades and is positive is **my proposal [P]**, as LADSPA's hint does].
* The units come from `value_to_text`: the control shows the number and the text the plugin gives for it [P].

## 7. Risks, in the order I worry about them

1. **The threads (C8).** If a plugin needs the real main thread of the process (some use the system's run loop), my worker is not that. *Mitigation:* the test plugin that checks, and the real set; the fallback is to run the main-thread calls on the editor's UI thread, which the contract names, at the cost of the graph waiting on the window.
2. **Latency compensation touches the graph (C9)**, which the null test holds to the old filter graph. *Mitigation:* a latency of 0 changes nothing, and the null test runs before and after; the new code is tested with the latency plugin to the sample.
3. **Plugins that need their window to say anything useful (C11, C12).** A person may put a plugin on a clip and find that its few exposed parameters do little. *Mitigation:* the window says so; this is the cost of not hosting windows, and the thing most likely to disappoint.
4. **The macOS bundle (7.8.2)** and the CI's macOS runner: untested by me [B]; a bundle is a folder, which the scan, the trust folder and the extraction of an embedded plugin all treat as a file today.
5. **A parameter that is not what it says** (an enum with a blank text, a range that is not finite): refused as a descriptor that cannot be used, and the plugin is listed as not used with the reason.
6. **Real plugins' scan time.** Some CLAP plugins take seconds to create (they load samples); the limit is 5 s for the whole library as now. *Mitigation:* the cache; a library that takes longer is failed with the step it was in (as now).

## 9. What 7.8.1 built, and what it found (2026-10-20)

### 16.2 The cause of Aura Lite's intermittent bad starts (2026-10-20, found with the plugins that can be bundled)

Eight other plugins (see `bundleable-clap-plugins.md`) put through the same lifecycle battery as Aura Lite: **0 differing new instances in 800 checks each** on seven of them (the eighth and ninth sound different on every run by themselves). Aura Lite: 1 of 200 on a lone new instance, 4 of 200 with another instance alive, 3 of 200 with another running. Then the experiment that explains it **[V]**: Aura Lite's sound at the start depends on what was in the heap before the plugin was made. Heap cleared: 0 of 100 differ; filled and freed with 0xFF: 86; with 0xCD: 90; with random bytes: 7; with audio-like floats: 0. What could be done (not done; waiting for the maintainer): **(1)** a check at scan time that makes the plugin twice, once in a cleared heap and once in a dirtied one, and marks a plugin whose sound differs as *unreliable at its start (it reads memory it did not write)*, so that a person is told rather than blamed; **(2)** making the memory that a plugin is given **zero** (a global allocator that clears what is freed, in a crate of its own with the one `unsafe`; it costs a memset of every freed buffer, which has to be measured, and it cannot clear what the video drivers leave); **(3)** hosting plugins in a process of their own (also isolates crashes; a phase of its own).
