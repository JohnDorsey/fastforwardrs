# Engine phase 15 report: VST3 plugins, each in a program of its own (2026-11-03)

*Labels: **[V]** = I ran it and saw it; **[B]** = I believe it from reading, and could not run it; **[CI]** = verified by a run of the continuous integration on Windows, Ubuntu and macOS, which I read. The design, with an "as built" section for every piece (8 to 16), is [`engine-phase-15-vst3-design.md`](engine-phase-15-vst3-design.md).*

## 1. What was asked

*"Support VSTs now ... run in their own process for crash isolation."* (2026-11-02.) Decisions taken with it, and kept: VST3 only (VST2 a later phase); a host of our own on the `vst3` crate's bindings; **a VST3 plugin always runs in a program of its own**, whatever the setting for the other formats says; effects and instruments; the plugin's own window as the second half.

**Asked on the way:** *"Get rid of the 255-value limit"* (done, section 11 of the design); *"I do want the other VST3 modules in the same release files"* (done: ten VST3 sets, the same download); and, after using it, *"Dragonfly Hall reverb's tail seems nonexistent after the clip ends"*, *"the slider motion is sometimes jerky"*, and then *"if I set the Decay to 10 seconds the tail gets cut short even when the tail length is Automatic ... I'd like a truly automatic option"* (sections 15 and 16).

## 4. What the maintainer should know (decisions I made, and what went wrong)

* **A VST3 plugin is never run in the editor's process.** `InAProcessOfItsOwn::includes` is true for every VST3 plugin whatever the setting says. The price: a missing or foreign `fastforwardrs-plugin-process` means no VST3 plugin is heard, and the effect says why.
* **No new file-format version.** The plan said one; the effect is named by its key and its descriptor is kept in `plugins`, so nothing in the layout is new. A program from before reads such a file as an effect whose plugin it does not have: kept whole, doing nothing. The limit of 255 values is the one thing a program from before would refuse (with the reason).
* **A tail is measured, not guessed (section 16).** I chose to run the effect and listen rather than raise the cap or read more tags, because the tail of a reverb is a function of its settings, and the scan sees it once. The cost is real: a thread, a second copy of the plugin in a program for half a second at each distinct setting, a number kept for the run of the program, and **a limit that I could not remove: a CLAP, LV2 or LADSPA effect that runs in the editor's own process is not measured** (a second copy beside the ones of a play could be a second alive at once, which some plugins forbid), so for those the guess of the scan stands.
* **An older fault found on the way and fixed:** the preview's detector of "the sound changed" did not look at an effect's tail at all, so a *Tail length* chosen in the menu while the sound played was not heard until the sound was made again for another reason.
* **A flaw of mine, caught before the commit:** the first version of the above hashed the bytes of a plugin's state at every frame in that detector (the code had been written, with a comment, to avoid exactly that). It uses the fingerprint that is made once, when the state is saved, now.
* **Mistakes of mine on the way that the tests caught:** a first test of the wake-up that could not tell a missing call (a window that closes says *Closed*, which wakes it all the same: it uses a crash now); a test that counted repaint callbacks, which egui merges (it reads which line of code asked for each frame instead); and the forgiving test plugins that hid host mistakes (they are strict now, and the planted-mistake runs said so: 32 of 36 noticed at first, 36 after).
* **I ran `drag_in_window.ps1`, which moves the real mouse, unguarded, early in 15.6**; it may have clicked on one of your windows. The tools that post messages to the plugin's window (`post_drag`) do not move the cursor and were used after.

## 5. What is open for the maintainer

* **The class id of a plugin built with DPF is not the same text on Windows and on Linux** (Dragonfly Hall Reverb is `445046206173636C3172666400000000` on Windows and `2046504473616C633172666400000000` on Linux: the same bytes read as numbers in the other order). A project with a DPF VST3 effect does not find its plugin on the other system. Surge XT's (written with the SDK's `INLINE_UID`) is the same on both. **Not changed: it is a choice about project files** (the key of an effect is in them); the options are to key on the bytes (and read old keys as either) or to leave it. *I recommend keying on the bytes, with a reader that accepts both texts,* and have not done it.
* **An animated Decay is not followed by the measurement.** Say so if you use one.
* **The tests of a real hand are not done:** the mouse was posted, not moved; resizing by dragging the frame; the keyboard's focus; a screen that is not at 100%; a second window of a plugin (a menu, a file chooser); macOS windows (written, compiled by CI, never made). Whether the slider is smoother after 532117a is **[B]**, not seen by me.
* **A panel with 774 values** (Surge XT) costs 27 ms a frame in release (31 µs a value, linear; 2,855 would be 102 ms); no folding, no search, no grouping by unit. I recommend row culling and did not do it (it changes the layout).
* **Scratch** is in `E:/s/sffrs/` (about 9.4 GB: the extracted real plugins, the mutation work copies, logs) and in WSL (`~/fastforwardrs/target`, 117 GB). Say if you want it removed.
