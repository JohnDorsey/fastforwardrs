# Engine phase 14 report: instruments in processes of their own (2026-10-30)

*Labels: **[V]** = I ran it and saw it; **[B]** = I believe it from reading, and could not run it. The design, with an "as built" section (6), is [`engine-phase-14-processes-design.md`](engine-phase-14-processes-design.md).*

## 1. What was asked

*"Run instruments in processes of their own. We might want to do the same with other sound plugins later."* The reason is the measurement of the day before: Surge XT dies at random (an access violation inside its own library, or a hang) when a patch is loaded as its state and notes are played, and a plugin that runs in the editor's process takes the editor and the project with it (`bundleable-synthesizers.md`, "Playing the patches").

## 3. What was checked

* **[V] The same bits.** `tests/plugin_process.rs` plays the same blocks through a copy in the test's process and a copy in the program, and demands that everything an effect looks at is the same, bit for bit: the sound, the latency, the control outputs, what the plugin asked for between blocks, and the words of a run that failed. CLAP instruments (with holds, releases, resets, all-off, the wheel), CLAP effects (values at samples, a latency, a tail, a plugin that asks to be made again, a state, a failure), LV2 instruments and effects (with meters and a state), LADSPA effects.
* **[V] The check that matters.** With every plugin forced into a program (a temporary switch, removed), **the whole library suite (5,878 tests), the 49 end-to-end sound tests with the real ffmpeg, the four plugin journeys, `application_sound` and `plugin_editor_sessions` pass unmodified**, at the same speed. Eight tests fail, and all eight are about the editor's own process: the breadcrumb written before the editor loads a library (4), which libraries the editor has loaded (1), the host waiting for the copies of a stream that is being stopped (3), and the bundle that the editor read once and keeps (1). They pass with `PluginHost::new()`, as they always did. Two of the three waiting tests show the point: a plugin that gives its sound with the sign changed when another copy of it is alive (found with a reverb that roared) is the same in two programs.
* **[V] What a plugin can do to its process** (`FFRS_TEST_PLUGIN` makes the test library do it): crash it while it runs, end it, hang it (the call is given up after its time limit and the program is stopped), crash it when the library is loaded, when the plugin is made or when it is activated, hang it there, print into it. Each is an error of one call or of the start, with the exit code in words, and the test program is still there. **A program ends when the editor closes its end of the socket, even if the plugin is in the middle of a call that never returns** (the thread that reads the socket ends the process). A program that the system stops from outside is an error of the next run.
* **[V] Real plugins.** Surge XT, Kars (CLAP and LV2) and Nekobi (CLAP and LV2) play a MIDI clip through the plan, the graph and a program of their own: silence before, sound in the notes, the tail, a note held across a seek (`tests/bundled_synthesizers_real.rs`, whose host is now made the way the editor makes it).
* **[V] What it costs.** Starting a program, connecting, loading and making the plugin: 55 ms for Surge XT (13 ms in the editor's process), so about 40 ms more at a seek. A block of 512 samples (10.7 ms of sound): 0.10 to 0.15 ms in the program, 0.015 ms in the editor's process: about 1.4% of real time for one plugin, 2.5 seconds in the export of a three-minute song.
* **[V] Planted mistakes: 35**, in the frames, the messages, the editor's side of a process, the program and the host's setting. The library's tests noticed 19 and the programs that run the real program noticed 15; **one was not noticed**: no test made the program fail while the plugin was being made, so the words for that case were not pinned. A test was added and it is noticed (`tools/mutation_testing/mutations_phase14_processes.py`).
* **[V] The whole workspace**: 6,565 tests passed, 0 failed, 56 ignored; the library suite passes when the new program is not built (5,887); clippy with `-D warnings`, `rustfmt` and `cargo doc` with `-D warnings` are clean on Windows; on Ubuntu (WSL) the new unit tests and both new integration programs (14 + 25 tests) pass.
* **[V] CI:** run 168 (`9f6cf6b`) passed on Windows, Ubuntu and macOS, and the licences and tools jobs (read 2026-10-30; 43 minutes), with the two known notices (the ffmpeg quirk for a picture of 65x48 and the real-time playback timing). The new tests ran on all three systems, so the program, the socket and the stopping of processes are checked on macOS too. Run 167 (`ea16a4f`, the phase itself) failed in Clippy on Ubuntu and macOS for one thing that was not in phase 14 (see 4).
* **[B]** Not seen: a window in which a person plays an instrument; whether Windows ever asks about a firewall for the program (reading the firewall rules needs an administrator).

## 4. What the maintainer should know (decisions I made, and what went wrong)

* **A socket and not the program's standard input and output.** A plugin may print to standard output (the scan program already has to read around it), a block of sound is binary, and a socket has a time limit on a read, which a pipe has not. It is a socket on 127.0.0.1 with a random token that the program says first, so that what connects to the port is known to be the program that was started. **[B] Windows has not asked whether the program may listen** (a socket on the loopback address does not trigger that question as far as I know): if it ever does, tell me.
* **A crash is an error of that play, not a restart.** The effect is left out for the rest of the play (the way a plugin that fails to run is), says why in its window, and the next play makes a new program. A restart in the middle of a play would lose the notes the instrument was holding, and the sound would be wrong without anyone being told. Say if you want it.
* **A program that is missing, or built from other code, means the instrument is not run** (and the window says to build everything with `cargo build --bins`), not that it runs in the editor instead: the point is that an instrument never runs in the editor. A fresh `cargo run` therefore plays no instrument until the other programs are built, as it shows no plugin window until the window program is.
* **`PluginHost::new()` still runs everything in the editor's process.** The editor and the export program ask for the instruments, and a test pins that for both. This keeps every test that was written before this phase running what it ran; the price is that a place that builds a host and forgets the setting is not protected.
* `Make` has no sample rate or frame limit (an earlier draft had them): the CLAP path ignored them, and a field that is ignored is a lie. Both sides use the constants of the sound engine.
* **Mistakes of mine on the way**, all caught by the tests before the commit: four tests that guessed wrongly how the test plugins behave (a state that makes one plugin abort works only in its window, not in the sound; a library "described" crash is the scan's, not the program's; a LADSPA copy has no meters; a generator cannot be an effect); a nonsense assertion that I wrote and removed; a first test run in which every `the_clap_kind_of` scanned the test library again (5 s each: 132 s for 14 tests, 8 s after the scan was kept); a first planted-mistakes run whose controls timed out because I had started a Linux build at the same time (rerun alone; the controls passed). And two that are from before this phase but are mine: **the commit `c1c0ce0` (the shorter paths for downloads) was not run through `cargo fmt`**, so the CI's *Format* step failed on it, and on the doc commit after it, on all three systems (runs 165 and 166; the tests never ran there); and when that was fixed, **Clippy failed on Ubuntu and macOS** (run 167) because a helper of the Windows-only curl test was dead code on the other systems (`9f6cf6b`). I had run Clippy on Windows only; **from now on Clippy runs on Linux too before a push** (`wsl ... run_in_wsl.sh cargo clippy --workspace --all-targets -- -D warnings`).

## 5. What is open for the maintainer

* **Surge XT's random crash is not reproduced through a program.** It needs a factory patch as the plugin's state and notes, and the 253 MB of patches that I fetched for the last report are no longer on this computer. What is shown is that a plugin which aborts, hangs, exits, or crashes when it is made does not take the test program with it. **If you say yes to fetching the patches again (253 MB, from the Bundles tab's own list), I will play patches that crashed before through a program, many times, and count how many programs ended and how many times the editor did.**
* A restart of an instrument inside a play (above).
* Other plugins: change `THE_PLUGINS_IN_A_PROCESS_OF_THEIR_OWN` to `Everything`; the whole suite passes that way except the eight tests of the editor's own process. The cost is 0.1 ms a block and about 40 ms at each seek for each plugin.
* A limit on the memory or the time of a program, and a process group so that a plugin that starts a program of its own cannot leave it behind (an operating-system feature of each system).
