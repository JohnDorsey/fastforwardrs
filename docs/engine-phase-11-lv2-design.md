# Phase 11 design: LV2 plugins

*Written 2026-10-26, after the maintainer said "I want LV2 plugins next, VST3 later or just through Carla". [D] is what was asked, [V] something I read or ran, [R] read in a web search on 2026-10-26 (not run), [P] my proposal, [B] belief.*

## 0. What was asked [D]

LV2 plugins, next. VST3 later, or just through Carla (a host that is itself a plugin and can contain others). Nothing about windows for LV2 yet.

## 1. What there is [V, read 2026-10-26]

* The program has **two plugin kinds** that make sound effects: LADSPA (`crates/ladspa-host`) and CLAP (`crates/clap-host`, on `clack`). Each is a crate with the `unsafe` in it (the root crate forbids it), a **scan** in a program of its own (`fastforwardrs-plugin-scan`; a scan that crashes does not take the editor with it; a start check runs a CLAP plugin twice to find one that reads memory it did not write), an `InstalledPlugin` (key `ladspa:...`, `clap:<id>`, an address `PluginAddress::{Ladspa, Clap}`, its parameters as the values of an effect), a **trust question per folder** (a library is loaded only from a folder that has been said yes to), and a `PluginInstance` that the sound engine runs in blocks with the values of the project (looked at every 32 samples where they have keyframes). Phase 10 added windows (CLAP only, a program of its own for each) and the plugin's **state** in the project (`state` of an effect, base 64, file format 19, given to the plugin before its values).
* **No LV2 host exists in this program.** No LV2 plugin is installed on the maintainer's machine now (I looked in `%COMMONPROGRAMFILES%\LV2`, `%APPDATA%\LV2` and `LV2_PATH`); some of the CLAP plugins they use (Surge XT, Dragonfly) ship LV2 builds as well, which is what to try first.
* **What LV2 is** [R/B]: a plugin is a **bundle**, a folder, with `manifest.ttl` (which names the plugin's URI, its binary and its description file), the description (`.ttl`, Turtle: the plugin's name, its **ports** with index, symbol, name, kind, default, range and port properties such as toggled, integer, logarithmic, enumeration and scale points) and the binary (a shared library that exports `lv2_descriptor(index)`). Control ports are single numbers read at each `run` (like LADSPA's); audio ports are buffers; **atom ports** carry messages (MIDI, and the messages that a plugin and its own UI send each other); **features** are things the host gives the plugin (a map from URI to number, `urid:map`, is the one every plugin needs), and each plugin says which it requires and which it only likes. The plugin's UI is a separate library with its own class (`ui:X11UI`, `ui:CocoaUI`, `ui:WindowsUI`, `ui:Gtk3UI`, `ui:Qt5UI`...); a host without it draws the controls itself from the ports, as this program's panel already does for every other plugin.
* **Hosts for it** [R]: `lilv` is the reference library (C; reads the Turtle through `serd`/`sord`, loads and instantiates, saves state); the Rust crate `livi` (MIT) wraps it through `lilv-sys` (MIT), which **links the system's lilv** and does not build it: nothing there says how to get it on Windows, so I do not count on it.
* **Carla** [R]: it is a plugin host that is also **an LV2 and a VST plugin** (Carla-Rack, Carla-Patchbay), and it can load VST3 (on Linux through JUCE's code). A note in its changelog says macOS and Windows "lacked native widget support for LV2" at one time; **whether its LV2 plugin works on Windows now I do not know [B]**, and it needs more of a host than a plain effect does (its own window, which it makes as an *external UI*, messages, state). So **"VST3 through Carla" is a thing to try once LV2 works, not a plan**.

## 2. What I propose [P]

**A host of our own in Rust, with no C library**: a crate `crates/lv2-host`, with the `unsafe` in it as the other two have, that
1. **finds bundles** in `LV2_PATH` and the usual folders (Windows: `%COMMONPROGRAMFILES%\LV2`, `%APPDATA%\LV2`; Linux: `~/.lv2`, `/usr/lib/lv2`, `/usr/local/lib/lv2`; macOS: `~/Library/Audio/Plug-Ins/LV2`, `/Library/Audio/Plug-Ins/LV2`), and the folders a person adds in the plugin manager;
2. **reads the Turtle** with a small, pure-Rust parser crate (`oxttl`, MIT or Apache, to be checked against `cargo deny`) into triples, and asks them the few things a host needs (the list above), the way `lilv` does and with the same files: manifests and descriptions are read from the bundle and nothing else (the LV2 specification's own files are not needed: a host knows the URIs it cares about);
3. **loads the binary and instantiates** (`lv2_descriptor`, `instantiate`, `connect_port`, `activate`, `run`, `deactivate`, `cleanup`) with the **features** below;
4. **saves and restores state** through the `state` extension (`save`/`restore` of a dictionary of key, type and value that the plugin stores through a callback), written as **our own bytes** (a list of URI, URI, flags, bytes) in the effect's `state`, so the project's file stays the same format (19) and a state is kept as it was when the plugin is not here.

**Why not `lilv`** (the other way to do it, and the one a person who knows LV2 would expect): it is C, built with its own tools, with four libraries under it; vendoring and building them on three systems in CI is work that `cc` can do but that I would be maintaining for ever, and the Rust crate that wraps it cannot be built on Windows as it stands. **Why not at once**: a Turtle reader plus a descriptor reader is about 1,500 lines, and the ABI of the features is the same size either way. **The risk of ours**: a bundle whose Turtle does something I did not think of (prefixes, lists, `owl:imports`, a port described in two files) is **not found by `lilv` as ours does not**; the answer is the scan says so for that plugin and a person says which, and I add it. [B, about 65% sure this is the better road; it costs a week of work if wrong, because the host's API (descriptor, instance, state) is what the rest of the program sees, and what is under it can be swapped.]

**Features to give a plugin** (a plugin that requires one that is not here is **not instantiated and the plugin manager says which**; **`log:log` is not given**: its `printf` is a function with a variable number of arguments, which stable Rust cannot define, and a plugin that requires it says so in the manager; the plugins that only like it go without): `urid:map` and `urid:unmap`; `opts:options` with `param:sampleRate`, `bufsz:minBlockLength`, `bufsz:maxBlockLength`, `bufsz:nominalBlockLength` (and `bufsz:boundedBlockLength`, `bufsz:powerOf2BlockLength` where they are true); `worker:schedule` (a thread that does what a plugin gives it, and the answers given back at the next `run`: many plugins require it); `state:loadDefaultState`, `state:makePath` and `state:mapPath` (**a plugin that keeps files (samples) in its state: its files go to a folder of the project's, and what they are called in the state is a path relative to it: the first version refuses a plugin that requires them and says so**); `lv2:hardRTCapable`, `lv2:inPlaceBroken` (the plugin gets other buffers for output than for input, which it asks for), `lv2:isLive` read and respected.

**What a plugin is, to the program**: an **audio effect** if it has audio inputs and outputs (one in and one out, two and two, one and two, two and one: the same as the other kinds); each **control input** is a value of the effect (the range, default and kind from its description: a toggle is a switch, an integer a whole number, an enumeration or scale points a list of choices, `pprop:logarithmic` a logarithmic slider); a **control output** (a meter) is not a value, except the port designated `lv2:latency`, which is the plugin's latency in samples and is read as CLAP's is. **Atom ports** get what keeps a plugin happy: an empty sequence for an input and a buffer for an output, thrown away after `run` (messages to and from the plugin's own UI are not carried, since there is no such UI yet). A plugin that is an **instrument** (MIDI in, audio out) is not an effect and says so, as a LADSPA one that is a generator does.

**Key and address**: key `lv2:<the plugin's URI>`, address `PluginAddress::Lv2 { uri, bundle }`, the library is the bundle's binary; a project carries the snapshot of the effect like any plugin's, and the effect is kept whole when the plugin is not found. **Trust**: the unit is the folder that holds the bundle (the folder in the search path), as for the others; an LV2 binary is loaded only from a folder that has been said yes to; the scan program reads Turtle and **does not load a binary** unless it has to (for the start check and for `lv2_descriptor`'s index), so the scan is cheaper and safer than the CLAP one.

**Threads** [B]: LV2 has few rules (`instantiate`, `save`, `restore`, `cleanup` not at the same time as `run` on the same instance; `run` on whatever thread the sound engine runs on). The sound engine's way with CLAP (a thread for the main-thread calls) is not needed; the worker has its own thread.

## 7. As built: piece 11.1 (2026-10-26) [V]

* **`crates/lv2-host`** (the third crate with `unsafe` in it; the audit test of the crate counts and demands a `SAFETY` note on every block) and **`crates/lv2-test-plugins`** (an LV2 library written in Rust for the tests, with the Turtle of its bundle written by `write_bundle`: nine plugins, a gain, one with every kind of control port, a latency, atom ports, options, a worker, one that requires `log:log`, a state, and one whose `instantiate` gives nothing). `oxttl` (and `oxrdf`) read the Turtle: pure Rust, MIT or Apache-2.0, passes `cargo deny`.
* **What is in it**: `description` (a bundle's Turtle into plugins, ports, features, extension data, user interfaces; loads nothing; a plugin that cannot be described is left out with its reason), `Library` (loads the binary, finds a plugin's descriptor by URI), `Instance` (made with the features; every port connected to something of the host's from the start; `run`; control values; latency from the designated port; the atom buffers made ready at each block; the worker on its own thread, stopped and joined before `cleanup`), and `state` (`save_state` and `restore_state` through `state:interface`, in bytes of our own that say URIs).
* **Features given**: `urid:map` and `urid:unmap`, `options` (sample rate, min, max and nominal block length, sequence size), `bufsz:boundedBlockLength`, `worker:schedule` (when the plugin lists it), and the markers `state:loadDefaultState`, `lv2:hardRTCapable`, `lv2:isLive`, `lv2:inPlaceBroken` that a plugin lists. Anything else that a plugin **requires** keeps it from being made, and the error names it.
* **Tests**: 36 in the crate, with the real test library loaded through the system's loader: the Turtle (every kind of port, languages, a file that is not Turtle, files that lead out of the bundle), the instance (a gain, a plugin that requires what is not given, one that gives nothing, block and buffer sizes, silent inputs, latency, atoms re-made at every block, options, the bundle path's separator, the worker's answer and `end_run`, a sample-rate default), the state (saved, given to another instance, a property missing, bytes cut short), the sizes of the structures of the interface on a 64-bit system, and the audit of the `unsafe` blocks. **The ABI is written from my reading of the headers, and the test plugin is written from the same reading**: a mistake in my reading would be in both, so the test that counts is a real plugin: [B] until the maintainer's bundles are tried (after 11.3).

## 8. As built: pieces 11.2 and 11.3 (2026-10-26) [V]

* **The scan** (`lv2_host::scan_bundle`, run by `fastforwardrs-plugin-scan` when it is given a folder with a `manifest.ttl`): the Turtle is read, the binary is loaded once for all of a bundle's plugins, and each plugin is made and run once on silence (a plugin that requires what is not given, that gives nothing at `instantiate`, or whose sound is not made of numbers is said, with the reason). `SCAN_FORMAT` is 5. The unit of the cache is the bundle; its fingerprint is the sizes of all its files added up and the latest time of any (down to four folders and five thousand files). `ScanAnswer::ScannedLv2`, `LibraryOutcome::ScannedLv2`, `CachedOutcome::ScannedLv2`, `ScanFailure::NotAnLv2Bundle`.
* **The effects** (`plugin_scan::effect_of_an_lv2_plugin`): key `lv2:<URI with its colons made underscores>`, version `(minor, micro)`, the category is the author, else the first kind it says it is, else *Plugins*; **the library of the effect is the bundle's folder** (so the trust is of the folder the bundles are in); the id of a value is the port's symbol and what the plugin is given is the number of the port; `PluginAddress::Lv2 { uri }`; the menu of the plus button has a smaller menu *LV2*. Folders: `LV2_PATH`, or the usual ones (`lv2_host::usual_folders`, given the system's places so that it does not read the environment), after those of the other kinds and before the bundled ones; a folder that a person adds is looked in for bundles too.
* **The sound** (`PluginHost`, `Lv2Copy`): the bundle is read once by the host (until a scan is done again: `forget_what_the_bundles_said`), the library once; a plugin is made as many times as the layout needs (a mono plugin on stereo sound is two); it is refused if it is not what was scanned (the audio ports or the control inputs are not those of the effect); the project's state is given before the values; a state that a plugin cannot take is said. **What the first run of the sound found (two defects, both fixed and tested):** (1) the effect gave a plugin a block longer than the plugin was made for (2048 frames for 512) when its values were not looked at in the middle of a block: **a plugin that takes so many frames at most is now given no more, whichever way it is told values**; (2) **an LV2 plugin says its latency when it runs**, so the host knew 0 until a block had been run and did not make the delay up: the instance is run once on 64 frames of silence when it is made, and is stopped and started again.
* **Tests**: `tests/plugin_scan_lv2.rs` (6; the real scan program and the bundle), `tests/sound_plugins_lv2_in_the_sound.rs` (6; the export and the preview with the real ffmpeg: the arithmetic of a plugin, keyframes, the latency made up to the sample, the state, a state that cannot be taken, a folder that nobody said yes to), `tests/sound_plugins_lv2_journey.rs` (the real editor: found in the background, offered in the *LV2* menu, put on a clip, saved, kept whole where the plugin is not and working again where it is), `src/plugin_scan/lv2_effects_tests.rs` (15; every kind of port by hand), the host's own 40, and three of the host of the sound. **Planted mistakes**: 56 in 11.1 (all noticed but one that is equivalent) and 44 in 11.2/11.3 (all noticed but one that is equivalent: a whole number prints without a point in Rust, and the code that said so was taken out).
* **Not done** (then; windows of LV2 plugins came in 11.5, section 10): instruments, files in a state (`state:mapPath`), `log:log`. **Real plugins**: none has been tried; the maintainer has none installed. Surge XT and Dragonfly Reverb ship LV2 builds.

## 9. Piece 11.5: windows of LV2 plugins [P, 2026-10-26; the maintainer asked for them]

**What an LV2 window is.** A plugin's bundle may name **user interfaces** (`ui:ui`): each is a class (`ui:WindowsUI`, `ui:X11UI`, `ui:CocoaUI`, and others that are not native to a system: `ui:GtkUI`, `ui:Gtk3UI`, `ui:Qt5UI`...), a binary (very often the plugin's own library, which then also exports `lv2ui_descriptor`), and the features it needs. **The UI is a separate piece of code that does not run the plugin**: it is made with the plugin's URI, the bundle's path, a `write_function` and a *controller*, and is given the host's features (the parent window, `ui:resize`, `ui:idleInterface`, `ui:touch`, `ui:portMap`, `urid:map`, the options); the host tells it the plugin's port values with `port_event` and it tells the host what a person did with `write_function` (port index, size, protocol, buffer). **Control ports are protocol 0: one `float`.**

**Decisions.**
* **The helper program gets a second kind of window.** `fastforwardrs-plugin-editor` is told `--kind clap` (the default) or `--kind lv2`; the *library* it is given for an LV2 plugin is the bundle's folder and the *id* is the plugin's URI (as in the project). The protocol of the editor and the program is not changed: **the id of a parameter is the port's index** (`value_handles` already are), and a gesture is a `touch` and a write.
* **A trait, not an `if`:** what the program does with a window (make it, embed it, size it, show it, tell it values, look at what it did, save and load a state, destroy it) is a trait `PluginWindow` with two implementations (the CLAP `Editor` and an LV2 one). The LV2 one is made in the program, on its main thread, **inside the window that `winit` made** (the parent is given at the moment the UI is made, which LV2 needs and CLAP does not: so the program passes the window to `make_the_window`).
* **A usable UI** (`lv2_host::window_of(plugin, api)`): of this system's class (`win32` is `ui:WindowsUI`, `x11` is `ui:X11UI`, `cocoa` is `ui:CocoaUI`), with a binary that is in the bundle, whose required features are all ones that this host gives. *The effect has a window (the button is in its box) exactly when there is one.* The plugin manager says nothing new; a plugin whose UIs are all Gtk or Qt simply has no button, as a plugin with no window has none.
* **The size.** LV2 has no call that asks how big a UI is. It is learnt from `ui:resize` (which most UIs call when they are made: DPF and JUCE do), and, **on Windows, from the client area of the window that the UI says is its widget**. If neither says, the window is 400 by 300 until the UI asks for another. The window can be resized by a person only if the UI has `ui:resize` as its extension data (it is told the size).
* **What the UI is told.** The values of the project, when it is made (the program was told them before there was a UI, so they wait), and after that each change. It is told nothing the plugin *makes* (a meter on a control output): **the plugin is not running in the window's program**, because the sound is made elsewhere; the window shows what a person sets, not what the sound does. *This is the one thing that LV2 windows do less than the CLAP ones, and it is said in the guide.*
* **State.** The window does not make a plugin's state: a state that a plugin keeps beside its ports is made by the UI sending atoms (`atom:eventTransfer`, `patch:Set`), which needs atom ports, the sound's instance in the same program, and the plugin's side of the conversation; **it is not built** (the window says `has_state: false`; a state that the project keeps is still given to the sound as in 11.3). A UI that only writes atoms is shown, and what it writes is thrown away.
* **Idle.** The UI is called `ui:idleInterface` every look (8 ms); an answer other than 0 means the UI closed itself, and the window is closed.
* **Headless** (the tests, no screen): the UI is made with the feature `ui:parent` that has **no data**, and the UI of the test library draws nothing then; with a window it draws a real child window (on Windows) so that a person can see it.

**What I cannot know until it is built [B]:** that a real plugin's UI (Dragonfly Reverb, Surge XT) works: the test UI is written from my reading of `ui.h`, as the test plugins were. The size on X11 and macOS comes from `ui:resize` alone, and I cannot run either here.

**Pieces.** 11.5.1 the host (`lv2_host::ui`, `UiDescription` gets the features and extension data, `window_of`); 11.5.2 the test UI (the gain plugin has one; the `fails` plugin has a UI that does not come); 11.5.3 the helper program (trait, LV2 implementation, `--kind`); 11.5.4 the editor (the effect's window is opened for an LV2 plugin; SCAN_FORMAT 6); 11.5.5 tests of each, and a real window on Windows; 11.5.6 the campaign and the docs.

## 10. As built: piece 11.5, windows of LV2 plugins (2026-10-26) [V unless said]

* **The host** (`lv2_host::ui`, `UiWindow`): loads the library of the interface, finds the interface in `lv2ui_descriptor`, makes it **inside a window of the program** (`ui:parent`: the handle is taken from the `raw-window-handle` of the window: a `HWND`, an X11 window id, an `NSView`; the window is kept by the interface's window as long as the interface lives), gives it `urid:map`, `urid:unmap`, the options (the sample rate and `ui:scaleFactor`), `ui:resize`, `ui:touch`, `ui:portMap`, `ui:idleInterface`, and turns what it does into `UiEvent`s (a write of protocol 0 and four bytes, a touch, a request for a size). `idle` is called at every look (8 ms); an answer that is not 0 closes the window. **A write of another protocol, of another size, or with no buffer is thrown away; so is a size that is not a size.** After `destroy` nothing is called any more (the plugin's `cleanup` was called once).
* **What a plugin says of its windows** (`UiDescription`: the features it requires and likes and the extension data it answers for; `window_of(plugin, api)`: the first interface, in the order of the URIs, of the class of this system with a binary and with nothing required that is not given; `SCAN_FORMAT` 6). **`has_a_window` of an LV2 effect is `window_of(...).is_some()`**, so the button is in the box exactly when a window can be shown.
* **The program** (`plugin_editor::backends`): `PluginWindow` is what the program does with a window; `ClapWindow` is the `clap_host::Editor` as it was and `Lv2Window` is the interface of an LV2 plugin. `--kind clap|lv2` (clap by default); for LV2 the `--library` is the bundle's folder and the `--id` is the plugin's URI. **The protocol is not changed**: the id of a parameter is the control port's index (what `value_handles` already are). Values told before the window is made wait and are given to the interface as it is made. A window of an LV2 plugin says `has_state: false` and, if it is asked for its state, gives back the one it was given.
* **The size.** From the system where it can say (Windows: the client area of the interface's widget), else from what the interface asked for with `ui:resize`, else 400 by 300 (`DEFAULT_WINDOW_SIZE`). **[B on macOS and Linux for a window that is shown: never shown there; CI has no screen, so what is tried on those systems is the headless path, which ran on Linux in WSL (52 host tests, 7 program tests, clippy).]**
* **Tests**: `crates/lv2-host/src/ui_tests.rs` and `ui.rs` (the host with the real test interfaces; the options and features that an interface is given, read back; 9 + 2), `description_tests.rs` (what an interface requires and answers to, which interface is a window, the order: 4), `tests/plugin_editor_lv2.rs` (the real program, headless, over the protocol, and the editor's side of it: 7; **and on Windows, a real window: the program makes a window of its own, the test interface makes a child window in it, and the size that the system says (380 by 250) is not the one the interface asked for (360 by 240)**), `tests/plugin_editor_lv2_journey.rs` (the real editor: the button, one step of history for a gesture, undo and redo, a value that closes the window, no button for a plugin with no window, a folder nobody said yes to: 3), `src/plugin_scan/lv2_effects_tests.rs` (when a plugin has a window), `backends.rs` and `program.rs` unit tests. A test of the same file, `look_at_the_window_of_the_test_interface`, is for a person: it opens the window and keeps it for `FFRS_LOOK_SECONDS` seconds (`--ignored`).
* **By eye** [V]: on Windows, with a real window, the program's window titled with the plugin's URI and the test interface's child window in it with its line of text.
