# Plugins and who may run them

How sound plugins are found, who may run them, how they run in the sound, and how the plugins that come with the program are bundled.

*Where a section says "see *Settings*" or the like, the section is in one of the files that `docs/README.md` lists.*

## Plugins and who may run them

*A sound plugin can be put on a clip, a track or a tag, keyframed, and heard in the preview and in the export. What decides whether one may be run is below, then the part that can load a library at all (a crate of its own, so that the rest of the program can go on forbidding `unsafe` code), a way of finding what is installed that cannot take the editor down with it (*Finding the plugins that are installed*), the plugins as effects (*Sound plugins as effects*), and running them in the sound (*Running plugins in the sound*).*

**A plugin is a program.** A sound plugin is a file of native code (a `.dll`, `.so` or `.dylib`) that the computer loads and runs with all the rights of whoever runs the editor, and **nothing checks what it does**. A project file can name one or carry one, so a project from somebody else could run anything. These are the rules:

* A project lists its **plugin libraries** (`plugin_libraries` in the file, format 14). A library is **linked** (a file somewhere, named by a path like a video; the path it was at and the same place from the folder of the project file are tried) or **embedded** (inside the `.ffrs` file, with one **build** for each kind of computer: a file of native code runs on one operating system and one processor, so `windows-x86_64` and `linux-x86_64` are builds of one library). Only a `.ffrs` file can have a library inside it. At most 64 libraries, 16 builds of one, 256 MiB for a build and 256 MiB for all the builds of a project (a project that says more is refused when it is opened, before any of it is read).
* When a project is **opened**, each library that has not been answered for is **asked about**, one after another, in a window that blocks everything else (nothing about plugins is an always-visible control). Plugins that are **files on this computer** (linked) are asked about **once for each folder** they are in (*Run plugins from this folder?*, with the libraries that are wanted named), and a *yes* is remembered for **the folder** (in `plugin_approvals.json` beside the settings file): what is in the folder, or comes to be, is not asked about again, and a file that is changed is run as it is. (It trusts the folder as a whole, so approve only folders whose contents you would run.) A folder is asked about when a project that has plugins on its clips is opened, when the scan finds a plugin that a project needed, when the sound first comes to a plugin nobody has answered for, and before an export; **a *no* holds for as long as the project is open**, and the sound goes through those plugins unchanged. A plugin **inside the project file** gets a severe question **every time the project is opened** (never remembered, not even after a crash): *This project contains a program: «name», for windows-x86_64. It runs with all your rights and nothing checks what it does. Load it only if you trust where this project came from.* **Don't load** is the default (Escape and closing the window are *no* too), and **Load it** cannot be clicked: it has to be **held down for five seconds**, with the mouse on it or with the Enter key, while it fills; letting go starts it over; and the Space bar does nothing.
* An embedded library with **no build for this computer** is not asked about: a message says which kinds it has. A linked one that is not where the project says is said so too.
* **Declining is safe.** A plugin that is not said yes to is a plugin that is not there: what uses it passes the sound through unchanged and keeps its settings, as any effect the program does not have does, and the project keeps the library and is saved with it as it was.
* Before an embedded plugin may be loaded it is **written out to a folder of its own** in the temporary files, and **checked against the SHA-256 that the project recorded for it** (a build that was changed or damaged is never run); the folder is removed when the program ends, and the folders that a run which was killed left behind are removed by a later one when they are a day old.
* **The command line cannot ask**, so `fastforwardrs-export` **refuses** a project that needs a plugin inside the project file, or a plugin in a folder that has not been approved, lists them, and exports nothing, unless it is given `--allow-plugins`. `--plugin-approvals <file>` reads the approvals from another file than the editor's. It looks for the plugins that the clips need (the folders in the file `plugin_search.json` beside the settings file, which `--settings` moves, and the usual places) with the same scan program the editor uses, and only when the project has effects that are not installed.

**Finding the plugins that are installed.** Plugins are looked for in the folders that a person adds, in the folders of the environment variable `LADSPA_PATH`, and in the usual ones (`/usr/lib/ladspa`, `/usr/local/lib/ladspa` and `~/.ladspa` on Linux and macOS; **Windows has none**: add the folder of the program that has them, such as the `plugins\ladspa` folder of LMMS). **A library is never loaded by the editor to find out what is in it.** The editor starts a program of its own, `fastforwardrs-plugin-scan <library file>`, which loads the library, reads what each plugin says of itself (its ports and the hints about them: range, default, toggle, whole number, logarithmic, a bound that is a fraction of the sample rate), then **makes each plugin and runs it once on 512 moments of silence**, and writes what it found. A library that crashes that program, never returns (it is stopped after **30 seconds**; it was 5 until the check of a plugin's start, below, which takes about half a second a plugin), says nothing, says something that is not the answer, or is not a library the system can load (an empty file, a damaged one, one that needs a library that is not there) is **failed, with the reason and what the scan was doing when it ended**, and the editor goes on. A plugin that cannot be made or run is listed with the reason, and the others of its library are not lost. What the scans found, failures too, is kept in `plugin_scan_cache.json` beside the settings and **is not tried again until the library's size or time of change is different** (so a library that crashes the scanner does not do it at every start; a scan of another version of the program is not believed). A **breadcrumb** (`plugins_in_use.json`) is meant for the time when plugins run in the editor itself: a library is written in it, and the file is flushed to the disk, before the first time it is used, and the file is removed when the editor ends well; one that is found at the next start says which library was in use when the editor ended badly, and the one that was started last is failed like the others. The scan program silences the crash windows of the system (on Windows) and core files (on Linux and macOS) for itself. **CLAP libraries are scanned in the same way** : a file that ends in `.clap` goes to the CLAP host (`crates/clap-host`, over the `clack` crates), which creates every plugin in it, activates it at 48000 Hz, runs one block of silence and reports its ports, parameters (with the texts of an enum), latency and tail. They are looked for in the folders a person adds, in `CLAP_PATH`, and in the places of the CLAP standard (`%COMMONPROGRAMFILES%\CLAP` and `%LOCALAPPDATA%\Programs\Common\CLAP` on Windows, `/Library/Audio/Plug-Ins/CLAP` and `~/Library/Audio/Plug-Ins/CLAP` on macOS, `/usr/lib/clap` and `~/.clap` elsewhere), **in the folders below them too (down to six)**; on macOS a `.clap` is a bundle, a folder, and it is the file inside it that is fingerprinted for the cache. **A CLAP plugin with a stereo or mono main input and output is an effect** : its key is `clap:` and its id, its category is its vendor, its parameters are its values (a stepped one is a whole number, an enum is a choice, a bypass is a switch, a range of a thousand times or more above zero is a logarithmic slider; hidden and read-only ones are not values), and it appears in the *CLAP* smaller menu of the plus button; it can be put on a clip and saved. **The question about a folder** reads *Trust plugins from this folder?*, names the folder, warns that plugins from the internet could contain viruses, and has *Don't trust* and *Trust*. **An effect of a sound plugin that does nothing is a placeholder that says why**: the folder is not trusted (not asked yet, or declined), the plugin is not installed (the scan is not done; the scan program was not found; its library failed, and how, including that it ended the editor badly; the library is there and has no such plugin; the plugin cannot be an effect and why; no such library or id in the folders that are looked in), or it went wrong when it was wanted (the library could not be loaded, it is not what was scanned, it could not be made or run, it was too slow); its values are kept. **The editor refuses a scan program that was built from other code than itself** (each is given an identity made from the contents of the code by `build.rs`; the editor asks the program for it before the first scan and says to build everything again with `cargo build --release --bins`). **It is run in the preview and in the export** , from a folder a person has said yes to, as a LADSPA plugin is: a value that has keyframes is told to the plugin **as an event at the sample** where its 32-sample stretch begins (the same places whatever the blocks are); a plugin that reports a **latency** is made up for to the sample (the effects of a clip are given that many samples more than the clip has before it is heard, and the first are thrown away); one that asks to be made again is made again between blocks (at most five times); the calls that CLAP wants on its main thread are done on a thread of the program's own. **The CLAP plugins that are really installed are tried by a report that runs on your computer** (`FASTFORWARDRS_CLAP_FOLDER=<folder> cargo test --test sound_plugins_clap_set -- --ignored --nocapture`, each plugin in a process of its own: whether the export and the preview make the same sound, whether it is a sound, whether it changed it, whether it makes the same sound twice, and how far a clip that begins in the middle is from the second half of the sound played through); the report is `docs/engine-phase-7-clap-report.md`. **A CLAP plugin that remembers is given sound from before the clip** : the feed of a clip begins that many frames earlier in the file (the tail the plugin says, up to two seconds; half a second where it says nothing; none for a clip that begins at the start of its file or is sped up, and none for a LADSPA plugin), the effects of the clip are run on it and what comes out is thrown away, so that a clip that begins in the middle of a reverb (a seek, a cut) begins as it would have played through. No window of a plugin, and no state, are hosted: its parameters are what the project keeps.

**A plugin whose start depends on memory it did not write** (a bug some plugins have: a roar, a warble or silence at random). After the scan has made and run a CLAP plugin once, it **makes it again after filling the memory with other bytes** and compares what it sounds like on a fixed noise (`crates/clap-host/src/start_check.rs`; design `docs/engine-phase-7-clap-design.md`, section 16.3). A plugin whose sound is different is **unreliable at its start**: the *Sound plugins* window says so under its library, and a note says so once while a sound that has it plays. It tells a person; it cannot make the plugin start well. It finds what a fill reaches (measured on Windows and Ubuntu; macOS not), takes about half a second a plugin, and is given 12 seconds for a library, after which its plugins are not checked.

**Plugins that come with the program.** GPL and LGPL plugins that are compatible with GPLv3 may be bundled, with their licence text and the corresponding source (**not AGPL, not GPL-2.0-only**). `bundled-plugins/manifest.json` names what is bundled (Dragonfly Hall, Plate and Room reverbs, MVerb, MaGigaverb and Surge XT Effects), each file with its checksum, its licence and where its source is; `py tools/bundled_plugins/fetch_bundled_plugins.py --out <folder>/plugins` (with `--with-source` for a release) checks the manifest against the licence policy, downloads the files, **checks every checksum before taking anything out of an archive**, and writes the licence texts and a `NOTICE.txt` beside each set. **A folder called `plugins` beside the program** (or the folder the environment variable `FFRS_BUNDLED_PLUGINS` names) **is looked in last, and trusted without the question** that other folders are asked, in the editor and in `fastforwardrs-export`; the window calls it *bundled with the program*. Nothing is distributed yet, so no release has made the folder. **The manifest has builds for `windows-x86_64`, `linux-x86_64` and `macos-universal`.** On macOS a CLAP plugin is a bundle (a folder): Surge's is a folder of a zip, and the others are taken out of the installer (`.pkg`) of a disk image, which the program mounts with `hdiutil` and expands with `pkgutil` without installing anything (the manifest's `installer` field). `FFRS_BUNDLED_PLUGINS=<folder> cargo test --release --test bundled_plugins_real -- --ignored` checks a folder that the script made: every plugin is found, loads, can be an effect, and starts steady (run on Windows and Ubuntu).

**The host.** `crates/ladspa-host` is **the only part of the program with `unsafe` code in it** (the editor keeps `#![forbid(unsafe_code)]`): it loads a library, reads the descriptors, makes instances and runs them, with a safe interface (an instance connects its ports to memory it owns or to buffers that are lent for one call, never leaves a plugin holding a pointer to memory that has gone, activates at the first block, deactivates and cleans up when it is dropped, and keeps the library loaded for as long as it exists). Every `unsafe` block says why it is sound and a test of the crate counts them (25 places; the list is in `docs/engine-phase-7-design.md`). The facts of the interface that are easy to get wrong are tested: `unsigned long` is 32 bits on Windows and 64 on Linux, so those fields are `c_ulong`; the places of the fields of the descriptor; the flags; the arithmetic of the defaults of the hints. `crates/ladspa-test-plugins` is a plugin library written for the tests, in Rust and from `ladspa.h` and not with the host's types (so the two agree only where the header makes them): a gain, a filter that remembers, a stereo swap, a toggle and a whole number and a meter, a plugin with no ports, a generator, mono to stereo, stereo to mono, and one that counts what the host does to it; and it can be asked to crash, never return, print noise, say nothing, give nothing or lie about how many ports it has. It is public domain (CC0).

**Sound plugins as effects.** *Edit, Plugin manager...* (it was called *Sound plugins...* until 2026-10-22, when ISF shaders were put in it too: see [`effects-and-shaders-in-detail.md`](effects-and-shaders-in-detail.md), *Shaders in the plugin manager*) opens a small window (it is not a control that is always there) where a person says where plugins are: the **folders to look for plugins in** (those of `LADSPA_PATH` and the usual ones are looked in too, and shown), the **folders with libraries that plugins need** (on Windows a plugin often needs a DLL that is not beside it: LMMS keeps `libfftw3f-3.dll` two folders above its plugins), and a checkbox, **on unless it is turned off**, to look in **the folders above each plugin library** too when the library it needs is not in the folders just named (nearest first, never the top of the disk). It says what the scan found (each library and how many plugins it has; the ones that failed, with the reason; the plugins that cannot be effects, with the reason), and has *Scan again*. Where to look is kept in `plugin_search.json` beside the settings. The scan runs in the background, at the start of the editor and whenever the places change, and never holds up the window; **a scan that failed for want of a library is tried again when the places to look for libraries change** (the others, a crash or a library that never returns, are not).
* **Each plugin that has an audio input and an audio output is an effect** (one in and one out, two and two, one and two, two and one) that can be put on **a sound or a video** (a video has a soundtrack), on a track and on a tag. A plugin with no audio input is a generator and is not an effect yet; its reason is in the window. **The menu of the plus button has a smaller menu for each place effects come from** (*Built-in*, *LADSPA*, and later *CLAP* and the others), and the plugins are in the *LADSPA* one under the heading of their maker, found by the search field (which narrows every smaller menu, and Enter adds the first effect that matches) by name and by maker; a smaller menu that is taller than the window has a scroll bar.
* **Each control input of a plugin is a value of the effect**, with the range its hint says (a bound that is a fraction of the sample rate is made into the value at 48000 a second), the default its hint says, a logarithmic slider where the hint says so, a switch for a toggle, a whole number for an integer; a value with a range that has only one end is a field to drag. A control output (a meter) is not a value. Values are keyframed like any other. Its key is `ladspa:` the library file's name without its ending, a colon and the label.
* **A project keeps what a plugin effect is made of**: the snapshot of the effect, its values and its keyframes are in the file. Where the plugin is not installed (or not found yet: the scan is in the background) the effect is **kept whole**, says *Not installed*, and is written back as it was; when the plugin is found it works, without opening the project again.
* **Windows of plugins** (phase 10, [`engine-phase-10-report.md`](engine-phase-10-report.md)): a CLAP plugin that has a window has **Open editor** in its box. The window is **another program** (`fastforwardrs-plugin-editor`, in the package and beside the editor; the editor asks it for its build and refuses one that is of other code), so that a plugin that crashes in its window does not take the editor with it. **The trust is the sound's**: the program loads the plugin library only if the library's folder has been said yes to, and says why not in the box if it was not (or was said no to). What the plugin saves of its own state is kept in the project (`state` of the effect, format 19, base 64, of any size) and given back to the plugin in the sound and in its window; it is bytes that only the plugin can read, and a project that is opened without the plugin keeps it as it was.
* **LV2 plugins** (phase 11, [`engine-phase-11-lv2-design.md`](engine-phase-11-lv2-design.md); **a host of our own, no `lilv`**): a bundle is a **folder** with a `manifest.ttl`. Bundles are looked for, one folder down, in `LV2_PATH` if it is set and otherwise in the usual places (Windows `%APPDATA%\LV2` and `%COMMONPROGRAMFILES%\LV2`; macOS `~/Library/Audio/Plug-Ins/LV2` and `/Library/Audio/Plug-Ins/LV2`; elsewhere `~/.lv2`, `/usr/lib/lv2` and `/usr/local/lib/lv2`), and in the folders a person adds in *Plugin manager...* (a folder of bundles). **The scan program reads a bundle** (its Turtle, then its binary: each plugin is made and run once on silence, as the others are) and the answer is kept in the cache of scans (a bundle has changed when the sizes of its files added up or the time of the latest change of any of them is not what it was). **The effect's library is the bundle's folder**, so **what is asked about is the folder that the bundles are in**, once, as for a library file; nothing of a bundle is loaded from a folder that has not been said yes to. A plugin is an effect if it has the audio ports of one (one in and one out, two and two, one and two, two and one); **an instrument (no audio input) says so and is not used yet**. Each control input is a value (a switch, a whole number, a choice among the scale points, a logarithmic slider, a range that is a fraction of the sample rate made into the value at 48000); a control output is not, except the one that says the plugin's **latency**, which is made up for to the sample (the plugin is run once on silence when it is made, because it says its latency when it runs). The host gives a plugin `urid:map` and `urid:unmap`, the options (the sample rate and the lengths of the blocks), `buf-size:boundedBlockLength`, the worker (on a thread of its own), and the markers `state:loadDefaultState`, `lv2:hardRTCapable`, `lv2:isLive` and `lv2:inPlaceBroken`; **a plugin that requires anything else (`log:log`, `state:mapPath`...) is not made, and the plugin manager says which**. Atom ports are given an empty sequence (an input) or room (an output) at each block. **The state** of a plugin (`state:interface`) is saved and restored in bytes of our own that say the URIs, and is given to the plugin before its values; **a window of an LV2 plugin does not make a state** (see the next paragraph), so nothing in the editor changes one. The bundle's Turtle is read again after each scan.
* **Windows of LV2 plugins** (phase 11, piece 11.5, [`engine-phase-11-lv2-design.md`](engine-phase-11-lv2-design.md) sections 9 and 10): an LV2 plugin whose bundle names **a user interface of this system's kind** (`ui:WindowsUI` on Windows, `ui:CocoaUI` on macOS, `ui:X11UI` elsewhere; the Gtk and Qt kinds are not shown) that asks for nothing that this program does not give (`ui:parent`, `ui:resize`, `ui:idleInterface`, `ui:touch`, `ui:portMap`, `urid:map`, `urid:unmap` and the options are given) has **Open editor** in its box, as a CLAP plugin does, and it is the same program (`fastforwardrs-plugin-editor --kind lv2`) and the same trust (the interface's binary is in the bundle, and the bundle is loaded only if the folder that it is in has been said yes to). **What a hand does in the window is the value of the effect** (control ports only: one `float`; a gesture is one step of the history) **and what the project says reaches the window**. **What it does less than a CLAP window:** the plugin is not running in the window's program (the sound is made elsewhere), so **a meter or any control output of the plugin does not move in the window**; an interface that talks in atoms (a sampler's file chooser, a preset list) is shown, and **what it says in atoms is thrown away**, so it cannot change the plugin's state; **a window of an LV2 plugin has no state of its own**. The size of a window is what the interface asks for with `ui:resize` and, on Windows, what the system says its window is; it can be resized by a hand only if the interface answers to `ui:resize`.
* **What the plan of the sound has:** each clip's plan carries its sound effects with their values and keyframes (and the frame it begins at), for the sound engine to do.

**Fetching the bundle from the program (the *Bundles* tab).** *Edit > Plugin manager...* has two tabs. *Bundles* lists the sets of `bundled-plugins/manifest.json` (the manifest is kept inside the program: name, authors, licence, source, and whether the set is fetched), and a button, *Download all (N MB)...*. The button asks first (how many plugins, how big, which sites, which folder, that every file is checked against a checksum kept in the program) and **nothing is downloaded before *Download* is pressed**. The download runs on a thread of its own, shows its progress, and can be cancelled (what was there before is left as it was). Each release file comes from its authors' own address over https (`curl --proto =https`, which also refuses a redirect to anything else), **its checksum is checked before anything is taken out of it**, only the files the manifest names are taken out, and each set gets its licence texts (from the addresses and checksums of the manifest) and a `NOTICE.txt`. A set is built beside its final place and put there only when all of it is there. The plugins go in `fastforwardrs/plugins` in the person's data folder (`%LOCALAPPDATA%` on Windows), a folder that is looked in last and trusted without the folder question (as the folder beside the program is); when the download is over the plugins are looked for. `curl` does the downloading (a separate program, as ffmpeg is: no library for the network is in the editor), and on Linux `tar` opens the archives. There are builds for Windows and Linux; a computer with none is told so.

**Running plugins in the sound.** The preview and the export ask the same code (`plugin_host`) to make the effect of a plugin, and the graph of the sound engine puts it in the clip's **insertions**.
* **Where in the sound:** the effects of a clip are done to its sound **before its volume**, one after another in the order of its chain. The effects of a **track** (and of a tag) are done to the sound of **each clip** where their badge is in the clip's chain, and not to the track once its clips are together: for an effect with no memory that is the same sound; for a filter or a reverb a clip ends where the effect's memory of it ends, and the next clip begins with the effect as it was made. (Making the effect of a track once, after its clips are together, waits for the groups of tracks.)
* **Channel layouts:** a plugin with **one input and one output** is made twice, one copy for each channel, with the same values; **two and two** is made once; **one and two** is given the mix of the two channels and its two outputs are the channels; **two and one** is given both channels and its output is both.
* **Values are exact at the frame the keyframes say:** a value that has keyframes is looked at **every 32 samples** (two thirds of a thousandth of a second) at the frame the first of them is in, and one that has not is given once and kept. A value is **kept to the range the plugin says** (a person can type one past its slider; the plugin is not given it). Playing from the middle of a clip gives the same samples as playing through to it, to the sample, where the plugin has no memory (tested with a gain that rises).
* **A plugin that remembers** (a filter, a reverb) is made again when the sound is made again; a seek makes the sound again, so it begins as the plugin begins. (A pre-roll, running the plugin for a while before the place a seek lands on so that its memory is warm, is not done.)
* **What a plugin gives that is not a number** (NaN, infinity) **or that is more than 1000 times as loud as the loudest sound there can be** (+60 dB) is **silence** in its place, and a note says so once; a plugin that fails to run is left out for the rest of that play and a note says so.
* **A plugin that is too slow** (it takes longer to make a block of sound than the block lasts, for two seconds of sound in a row) is **left out of the preview** for the rest of that play, the sound going through it unchanged, and a message says so, once. **The export waits for it and never leaves one out.**
* **The same sound:** the preview and the export make the same samples (tested to the sample with the real ffmpeg and the test plugins, with and without keyframes), and a clip with no plugin on it is made by the host exactly as it is made without one.
* **Who may be run, in the sound:** a plugin in a folder nobody has said yes to is **not run**: the sound goes through it unchanged and the editor asks about the folder (above); when the answer is *yes* the sound is made again with the plugin in it, without anything else being done.
* **The libraries that plugins need** are looked for where *Plugin manager...* says (the folders named, then the folders above the plugin library if the box is checked, which it is unless turned off) when the editor loads a plugin to run it, as the scan does. On Windows this is done by putting those folders in front of the search path of the process before the library is loaded; the other systems read their search path when the program starts, so a library that needs one that is not beside it is found by the scan (which is started with the folders) and may not be by the editor: *[B] not tried on Linux or macOS*.
* **The breadcrumb is written now:** a library is written in `plugins_in_use.json` and flushed before the first time the editor loads it, and the file is taken away when the window is closed; one found at the next start fails the library it was using (the last one started) in the scan cache and says so in a message, and the library is not loaded again until the file changes.
* **Plugins run in the editor's own process** (the host is `crates/ladspa-host`): a plugin that crashes takes the editor with it, and the breadcrumb says, the next time, which library it was. That is the price of running them at the speed of the sound; the scan, which tries every plugin once in a program of its own, is what makes it rare.
* **A real set:** `tests/sound_plugins_lmms_set.rs` (ignored; run it on your computer with `FASTFORWARDRS_LADSPA_FOLDER` set to a folder of LADSPA libraries) puts **every plugin that can be an effect on a clip, each in a process of its own**, makes a second of noise with it by the export and by the preview, and reports for each whether the two made the same sound, whether it is still a sound, whether it changed it, how loud it is, and what the plugin said; a plugin that crashes or hangs takes only its own process.

**A plugin inside a project file runs without being installed (AU-13, built 2026-10-21).** When *Load it* has been held down, the build for this computer is written out to a folder of its own in the temporary files (`<hash>-<platform>/<name>`: the file keeps its name, and a build is a folder, so a yes is for that build alone), checked against the hash the project recorded, scanned in the background by the scan program, and its plugins are installed after those of the folders (an installed plugin of the same key wins). **It lasts as long as the project is open**: when another project is opened the folder is not trusted any more and the plugins are not installed, and the question is asked again whenever the project is opened. The command line does the same for every library with a build for this computer when it is told `--allow-plugins` (a build that is not what the project recorded refuses the export). An effect whose plugin is inside the project and has not been loaded says so in its window. No window can embed a plugin yet (that is the plugin manager, phase 8): a project file made by hand or by a test carries one; the library kinds are `ladspa` and `clap` (a CLAP bundle, a folder, on macOS cannot be carried yet).

**Not built yet:** generators (plugins with no audio input); the effects of a **group** of tracks; a pre-roll for plugins with memory.
