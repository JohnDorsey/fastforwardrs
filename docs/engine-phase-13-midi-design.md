# Engine phase 13: MIDI clips and synthesizer effects (design, draft 1, 2026-10-28)

*Draft written before any code. Labels: [V] = I looked at the code or ran it; [B] = I believe it from reading or from memory of a standard; **Q1..Q4** = questions only the maintainer can answer (asked in the chat), each with the answer I would choose. Nothing in this file is built.*

## 1. What the maintainer decided

* A **MIDI clip** feeds **synthesizer effects**.
* **No automatic pass-through:** a synthesizer is the **sole consumer** of the notes that reach it, unless the person says otherwise (by default it consumes them).

## 2. What exists today [V]

* **No MIDI anywhere in the program.** `ClipKind` has Video, Audio, Image, Text, Crate, Adjustment, Generator (`src/project/tracks/clip.rs`). The word "MIDI" appears only in the LV2 description reader (a port that says it supports `midi:MidiEvent` is read and then ignored) and in notes that say "not done".
* **The CLAP host sends parameter events and nothing else** (`crates/clap-host/src/instance.rs`: `input_events` gets only `ParamValueEvent`s; the scan reads audio ports and not note ports).
* **The LV2 host gives an atom port an empty `atom:Sequence`** (`crates/lv2-host/src/instance.rs`), so it can be filled with events later; the buffer layout code exists.
* **The scan refuses every plugin with no audio input** with "a generator or an instrument is not used yet" (`src/plugin_scan/effects.rs`, three places: LADSPA, CLAP, LV2). So no synthesizer is an effect today.
* **LADSPA has no notes at all** [B]: it stays effects-only for ever (DSSI was its instrument cousin; not planned).
* **Real synthesizers are already fetched by the Bundles tab** (per `docs/bundleable-clap-plugins.md`): Kars and Nekobi (DISTRHO), Surge XT (a CLAP in a zip that also has the effects one). `clap-test-plugins` has a test instrument (no audio input, a note port); I did not check that it makes sound from a note, and I expect it needs to be given that.
* **A text clip is "a clip whose content is the effect `builtin:text`"** (phase 9). A MIDI clip can be built the same way round, or as a clip with its own content; see 4.
* **The sound engine already has what a synthesizer needs around it**: one instance of a track's effects per run (the bus), tails (a synthesizer's release rings after the last note off, like a reverb), the lead-in (a seek begins up to 10 s early, unheard), the edge fade, windows. Notes have to travel the same paths as the sound does.

## 3. The model, in one paragraph

A MIDI clip has **notes** (and, later, controllers) and **makes no sound itself**. Its notes flow along the same road that sound flows along: **the clip's own effects, then its track's effects, then the effects of the clip groups it is in, then those of its track groups** (the order of `SoundClip::sent_to`). At each synthesizer on that road the notes are **consumed**: the synthesizer plays them and **the notes go no further**. A synthesizer **makes audio**, and that audio continues along the road as sound, through the effects after it. If no synthesizer is on the road, the notes are dropped and the clip is silent (and the clip is drawn so that this is visible: Q2).

## 4. Pieces (each is built, verified and committed before the next)

**13.0 Lock what is.** Tests that pin the scan's refusals, the sound plan's shape for a track with effects, and the file format, *before* anything changes (as for phases 9 and 12).

**13.1 Host: notes into plugins.**
* *CLAP*: read the note ports (`clap.note-ports`: how many, which dialects, which is preferred) in the scan, send `NOTE_ON`/`NOTE_OFF`/`NOTE_END` events with a sample offset inside the block, and (if the plugin takes the MIDI dialect) controllers and pitch bend as MIDI events. Choke and all-notes-off when a window ends. A note id for each note, so that releases are matched.
* *LV2*: fill the atom input port with MIDI events (`atom:Sequence`, time in frames, `midi:MidiEvent`); ports that are not MIDI stay as they were.
* The test instrument makes a tone from a note, so the host is tested without a real synthesizer; real ones (Kars, Nekobi, Surge XT) are tried after.

**13.2 The synthesizer as an effect.**
* The scan stops refusing a plugin with **no audio input and a note input**: it becomes an `EffectKind` of the sound domain with a flag *makes sound from notes*. (A plugin that has both an audio input and a note input, such as a vocoder, takes its audio from the road as an effect does and its notes as a synthesizer does: no special case.)
* It sits in a chain like any sound effect and has its values, keyframes, presets and window like any plugin (the work of phases 7, 10, 11 does not change).
* **Audio that reaches a synthesizer on the road passes by it** and the synthesizer's own audio is added to it (Q1).
* The sharing setting of the track (phase 12) decides how many instances there are: one for each clip, one for a run of clips, one for the whole track: so a synthesizer on a track has one set of voices for all its MIDI clips, and a synthesizer on a clip has its own.

**13.3 The MIDI clip in the project.**
* New `ClipKind::Midi`; file format 21; undo and redo like other clips; trim, split, move, duplicate, speed, mute work as for a sound clip.
* Content: the notes, in **seconds of the clip's own time** (the tempo map of the file is applied at import; the project has no tempo or bars, Q4), with pitch, velocity, channel; controllers and pitch bend in a second list.
* **Speed changes the timing and not the pitch** (the program's own idea: shrink when sped up).
* **Edges:** a note that began before the clip's first frame is not played; a note that is still held at the clip's last frame gets its note off there (the synthesizer's release rings on as a tail, under the tail policies of phase 12).
* **Mute** of a MIDI clip stops its notes (note offs for what was held). Volume of the clip is *not* velocity: it is the volume of what the clip's own effects make, which is nothing if the synthesizer is on the track (stated in the menu text).

**13.4 The plan and the engine.**
* `composition::sound`: a MIDI clip makes a **`NoteClip`** item with the notes and the same `sent_to` and tail routes as a `SoundClip`; `SoundPlan` finds, for each synthesizer, the notes that reach it (the walk of section 3), and the plan is hashed so that moving a note re-makes the sound.
* `sound_engine`: each instance of a synthesizer gets, in each block, the notes of its clips with sample offsets (sample-exact, not frame-exact); notes are consumed there (not sent on) unless the setting of 13.5 says otherwise. **A seek** runs the lead-in as for sound, and a note held longer than the lead-in is *chased*: it is started at the seek (Q3 asks nothing, I decided this; say so if wrong).
* The ffmpeg oracle of the export tests cannot play a synthesizer: the export is compared with the preview, and a null test uses the test instrument, whose tone is exact arithmetic.

**13.5 The one thing that is not the default: letting notes pass.**
* How the person turns it on is **Q3**. Whatever it is, it is stored with the effect (a saved project keeps it), is undoable, and is shown on the effect's box.

**13.6 What the person sees and does.**
* A MIDI clip on the timeline shows a small **piano roll** of its notes (read-only), a title, and a marker when no synthesizer is on its road.
* The **Plugin manager** lists synthesizers as sound effects, in a group of their own.
* **Where the notes come from is Q4**: importing `.mid` files (small; `midly` is `Unlicense`, which `deny.toml` allows [V by `cargo info`], or a reader of our own: the format is simple) is in; a **note editor** is a large piece on its own.

**13.7 Real use.** Kars, Nekobi and Surge XT played from a `.mid` file, listened to, a window opened, presets; the report `docs/engine-phase-13-report.md`.

## 5. Risks, in the order I would worry

1. **Sample-exact events with the engine's blocks and latency compensation** [B]: the engine delays members to line up effects with latency; notes have to be shifted the same way, or a synthesizer is early.
2. **Tails and chokes at the edges of clips, groups and windows**: a note that is held while a group's window closes. The phase 12 machinery covers the audio; the notes need their own note offs.
3. **A plugin with a window that plays by itself** (an arpeggiator in a synthesizer) is fine; one that *sends* notes out is not supported (output events are ignored, as now).
4. **Disk and CI**: the real synthesizers are large sets; the tests use the test instrument, the real ones go in the integration tests that are `#[ignore]`d without the bundled plugins, as for the effects.

## 6. Left out (named so that it is a choice and not an accident)

MIDI **effects** (arpeggiators, chord makers, transposers that take notes and give notes: the road above has room for them, as a note-in note-out kind of effect that does *not* consume) · MPE and per-note expression · MIDI 2.0 · recording or live playing from a keyboard · a project tempo, a bar grid, quantise · LADSPA/DSSI instruments · a synthesizer that sends notes out · sidechain notes · sampler instruments that keep files in their state (refused already for LV2).

## 7. The maintainer's answers (2026-10-28)

* **Q1** Audio that reaches a synthesizer **passes by it, and the synthesizer's sound is added**.
* **Q2** Notes find a synthesizer **by position, the first one on the road wins**; a MIDI clip with none on its road is silent and carries a marker.
* **Q3** A synthesizer lets notes pass on by **a switch on the synthesizer** (off by default; saved, undoable, shown on its box). No separate "pass notes" effect.
* **Q4** Notes come from **`.mid` import only** in this phase; each MIDI track of a file becomes a clip on its own timeline track, drawn as a read-only piano roll. The note editor is a later phase of its own.

Decided by me and not asked (say so if one is wrong): the notes are stored in seconds with the file's tempo map applied (no project tempo); speed changes timing and not pitch; a note begun before a clip's first frame is not played and one held at its end gets a note off there; a held note longer than the 10 s lead-in is chased at a seek; MIDI effects (note in, note out) are left out, and the road has room for them.

### 13.1 Host: notes into plugins (2026-10-28)

* **CLAP** (`crates/clap-host`): `ScannedPlugin::note_inputs` (`NotePort`: id, name, the dialects the port takes, the one it prefers; an old scan without the field reads as none); `Instance::note_inputs()`; `Instance::run_with_notes(inputs, outputs, changes, notes)` with `NoteEvent { time, what: NoteEventKind::{On, Off, Controller, PitchBend, AllOff} }`. Notes go to the **first** note port, as CLAP's own events if it takes them (`NOTE_ON`, `NOTE_OFF`, all off = `NOTE_CHOKE` of everything), otherwise as MIDI; **controllers and the wheel only as MIDI** (a port that takes only CLAP's events is not given them). Notes and parameter changes are merged by time, the change first at the same sample. The host says it has `note-ports` (CLAP and MIDI). `run` is `run_with_notes` with none.
* **LV2** (`crates/lv2-host`): `Instance::takes_midi()` (the first atom input that supports `midi:MidiEvent`), `Instance::run_with_notes(inputs, outputs, frames, notes)`; the notes are written into that port's `atom:Sequence` (`notes.rs`: 16-byte header, then each event as an `i64` frame, the atom header, the 3 bytes padded to 8: 24 bytes each; **events that do not fit in the 64 KiB buffer are left out**; all off = controller 120 on each of 16 channels; a note at or after the block's end is `RunError::NoteOutsideTheBlock` and nothing is run). MIDI velocity: 7 bits, a note on is never 0.
* **Test instruments**: CLAP `…test.instrument` (CLAP and MIDI note port, prefers CLAP; deaf to controllers, the wheel and MIDI all-sound-off, so that a choke has to come as CLAP's event) and `…test.instrument_midi` (MIDI only; reads the wheel, the pedal and all-sound-off of its channel); LV2 `urn:fastforwardrs:test:instrument` (same arithmetic as the MIDI one, and says on a control output how many events the block had). The sound is plain arithmetic: while notes are held, every sample is the sum of `velocity * key / 100` (+ wheel `(w - 8192) / 8192 * 0.5`, + pedal `v / 127 * 0.25` while a note is held).
* **Checked [V]**: 15 tests in `clap-host/src/note_tests.rs`, 16 in `lv2-host/src/note_tests.rs` (exact samples, exact bytes of the sequence, the room, both kinds of event); **17 + 21 planted mistakes, all noticed** (the CLAP campaign found four gaps at first: a note off sent as a note on [the test's offs had velocity 0], the all off that only the MIDI path made [the first instrument also read MIDI all-sound-off], the order of notes and parameter changes [no parameter to see it by: the instruments got `Gain`], and `run` giving an event); whole library suite 5578 passed, clippy and rustfmt clean on Windows and Linux (WSL), the new host tests also pass on Linux.
* **Not done / known gaps**: a CLAP plugin with several note input ports is only given the first; the `note_id` of a CLAP note is the caller's (the engine will make them in 13.4); output events of a plugin (notes it sends out) are still ignored; `Controller` and `PitchBend` are untested against a port that takes only CLAP's events (there is no such test plugin: the code path is a `match` guard that drops them).

### 13.2 The synthesizer as an effect (2026-10-28)

* **What makes a synthesizer** (decided by me, and not asked: say so if it is wrong): a plugin with **no audio input and a note input** (CLAP: a note port that takes CLAP's events or MIDI of the first kind; LV2: an atom input that supports `midi:MidiEvent`). **A plugin that has an audio input is an effect even if it also has a note or a MIDI input** (a vocoder, an effect that a note triggers): it hears sound, and notes are not its to take, so it will not take notes from a synthesizer that is after it. One output, mono or stereo (a synthesizer with three or more is refused with the reason). A plugin with no audio input and no note input is still a generator and still not used.
* **The flag** `EffectDescriptor::makes_sound_from_notes` (`EffectKind::makes_sound_from_notes()`): in the snapshot of a project file as `"makes_sound_from_notes": true` (left out when false, and in older files; **no new file format number**, since an older program keeps an unknown field as it was). **It is part of what a plugin must agree with to stand in for a snapshot** (`can_stand_in_for`): a file that says an effect is not a synthesizer is not given a synthesizer of the same key, and the effect is kept whole. The scan cache is `SCAN_FORMAT` 8 (the note ports of CLAP plugins are new).
* **In the effect** (`plugin_host`): two new layouts, `MonoSource` (0 in, 1 out; both channels get it) and `StereoSource` (0 in, 2 out), one instance each. **The sound that reaches the effect passes by and what the plugin makes is added to it** (an effect's replaces it). `PluginInstance::run_with_notes` (CLAP, LV2; the default is `run`), and `BlockProcessor::give_notes(&[NoteEvent])`, said before `process`: a synthesizer keeps them for that block and is given each piece (the block is cut into pieces for a plugin that takes at most so many frames, or for values at the samples where keyframes look) the notes that are in it, counted from its start; a note at or after the end of the block is given to no piece; **an effect that is not a synthesizer lets them go**. A sound that a synthesizer makes that is not a number, or is far too loud, is silence in its place and is said once (as for effects); a synthesizer that fails is left out and the sound goes by unchanged.
* **The notes of the program's own** (`sound_engine::NoteEvent`, `NoteEventKind`): one type, made into `clap_host::NoteEvent` and `lv2_host::NoteEvent` (which has no `id`).
* **Not yet**: nothing gives a synthesizer notes (13.3, 13.4: there are no MIDI clips yet), so a synthesizer put on a clip is heard as silence added to its sound; the properties panel and the plugin manager list synthesizers as sound effects with no sign that they are played by notes (13.6); **a LADSPA plugin is never a synthesizer** (the format has no notes). The tail of a synthesizer is its plugin's (the release rings on as a tail, under the phase 12 rules); a reset (a seek) lets go of its voices in the test instruments, and **I did not check what the real instruments do** (Kars, Nekobi, Surge XT are for 13.7).
* **Tests that pinned the old refusals and changed on purpose**: `plugin_scan_clap.rs` (the library's effects are 17 and not 15, three not used and not five: the two instruments are effects with no audio input, two outputs and the flag), `plugin_scan_lv2.rs` (8 and not 7 effects, two not used and not three), `sound_plugins_clap_journey.rs` and `sound_plugins_lv2_journey.rs` (the counts), `plugin_host/tests.rs` (the layouts are six, with the two sources refused only for 0 in and 0 or 3 out), `plugin_scan/tests.rs` (`SCAN_FORMAT` 8). The refusals that stay: a plugin with no audio input and no note input says "no audio input and no note input" (LV2: "no MIDI input"), and LADSPA's.
* **Checked [V]**: 9 tests with the real CLAP and LV2 test instruments through `PluginHost::processor_for` (`tests/synthesizers_in_the_sound.rs`: exact samples added to sound that passes by, in both kinds of event, a value of the plugin heard, a note that goes on in the next block, a reset, the choke that only CLAP's event gives, the wheel and the pedal, an effect that is given notes does nothing with them), 10 of the effect with a plugin instance written for the tests that records what it is given (`plugin_host/synthesizer_tests.rs`: both layouts, the notes cut into pieces, a note outside the block, not a number, a plugin that fails), 12 of the scan (`plugin_scan/synthesizer_tests.rs`), 3 of the project file, 3 of the notes; **28 planted mistakes, all noticed in the end** (4 first survived or were skipped by a changed text: the notes that the engine's own type moves earlier and the conversion into each host's type had no test of their own, because the effect only asks for notes that are in the piece).

### 13.3 The MIDI clip in the project (2026-10-28)

* **A decision of mine that the maintainer did not ask about, and that the design had not said: the MIDI file is a *resource* of the project** (`ResourceKind::Midi`, key `midi`), not a source of media. The resources already do what the file needs (included in the project file as it is, or linked by two paths; two files with the same bytes are one; at most 64 MiB; read once and kept; a linked file that is gone leaves the resource *missing* and the clips that use it are kept; one that nothing uses is not saved), and a source of media is a thing that ffprobe, the thumbnails, the waveforms and the decoder of the sound all assume is a video or a sound. `Resource::midi_file()` reads the bytes as music once (an `Arc`, shared by the copies of the project, and not a part of what makes two resources equal); `cube_table()` and `midi_file()` each refuse a resource of the other kind. **The cost: a project file that has a MIDI clip is refused by a version of the program before this one** (file format 21, which it would refuse anyway).
* **13.3a, the reader** (`src/midi_file.rs`, commit 4ad071c; no dependency, since the format is small): see its head. Format 0 and 1; ticks to a quarter note and SMPTE; times are whole microseconds worked out exactly from the tempo map of all the tracks; notes paired FIFO by channel and key; a track that is cut short is read as far as it goes and the file says so in `problems`; a file that cannot be read says why. 37 tests, 33 planted mistakes (the one that was not noticed was a branch that cannot be reached, which is gone).
* **`SourceSpan`** (`project/tracks/source_span.rs`): the first source frame, the end, the speed, and **all the arithmetic that a clip of a video and of a sound had in `MediaClip`** (every Nth frame, a partial group counted; where a timeline frame is in the source; the cut; counting again at another frame rate), moved out so that a MIDI clip cannot count differently. `MediaClip` has one and delegates; **its tests were not touched** (the gate), and the 1262 tests of the project and the composition passed before and after.
* **`MidiClip`** (`project/tracks/midi_clip.rs`): the name of the resource, which track of the file it plays (its place, from 0), a `SourceSpan` (**a frame of the source is a stretch of the music as long as a frame of the project's video, from the start of the file**, counted again when the project's rate changes), a volume and a mute switch. `Clip::Midi`, `ClipKind::Midi`; `is_media()` is true for it (it has a speed, and **the clips after it are carried along when its length changes**, as for a sound), `as_media()` is `None`, it has no source file, no placement on the picture and no duration of its own. **Its speed changes when its notes are played and not what they are** (the length of a clip is the length of its music over its effective speed, as for a sound clip), which is what the design said.
* **What it has:** the properties volume and mute (with keyframes), sound effects (the synthesizers among them; **not picture effects**: a picture effect on it is refused, and a file that has one is refused with the reason), the speed, the cut, the move, the rate counted again. `Project::try_insert_midi_clip(track, frame, clip)` (room for all of it, the rules of groups) is what a test and the import (13.6) put one on a track with. `Project::resources_in_use()` has the files of MIDI clips, so a file that a clip plays is saved, and one that none plays is not; `resources_in_use_that_are_missing()` says one that the project has not, or that is missing.
* **The file** (format 21): `"kind": "midi"` with `resource`, `midi_track`, `first_source_frame`, `end_source_frame`, `speed_factor`, and `gain_decibels` and `muted` when they are not the defaults, `drawer`, `effects` and `badges` as the other clips; `deny_unknown_fields` as they do. A file of version 20 is read as before.
* **In the window:** the clip is drawn in violet with its label (**the name of its file and, if its track has one, of its track**: `tune.mid · Melody`); its box in the properties panel has the name of its file, its speed, its volume and its mute switch (the three rows are what a video and a sound have, as one function now); `kind_name` is "MIDI clip", and what tells one from another is the name of its file; the command that sets a speed knows that a MIDI clip plays at its own speed already (it was the media clip's alone). The signature of the sound (what makes the sound begin again when something is edited) has the MIDI clips: their file's name and bytes (CRC-32), their track, their run, speed, volume, mute and keyframes.
* **Not yet:** nothing plays a MIDI clip (13.4: `composition::sound` still has no note item, so **a MIDI clip makes no sound**, and says nothing of it: the marker of 13.6 is not built), no piano roll and no import (13.6), no command that puts one on a track.
* **Checked [V]:** 44 new tests besides the reader's 37 (the clip itself 6, in the project 11, in the file 9, in the window 5, as a `Clip` 4, the resource kind 5, the signature of the sound 1, the naming 1, the label 2), **35 planted mistakes in the clip, the file, the resource and the window: 33 noticed; the two that were not are equivalent** (a MIDI clip and a sound clip have the same effects, so the one kind named in the file's reader for the other changes nothing; and the check in the command that sets a speed that a clip is at it already is only a shortcut: a clip that is given the speed it has is not changed by the project either); whole workspace (5687 library tests, every integration program) passed, clippy and rustfmt clean on Windows.

### 13.4 The plan and the engine: how the notes get to a synthesizer (design, 2026-10-29; written before the code)

**Where the notes go is decided in the plan, once, and not while the sound is made.** A MIDI clip makes a `SoundClip` like any other clip that has no sound of its own: the same item, the same chain of its own effects, volume, `sent_to`, tail routes, and the same stretches that its mute switch cuts it into. What is new is `SoundClip::music: Option<Music>` (and `source` is `None` for it): its notes (and controllers) for that stretch, in **samples counted from the start of the stretch**, and **who plays them**: `NoteConsumer::Clip` (the first effect of its own chain that is a synthesizer: an effect whose kind has `makes_sound_from_notes`, installed or not, so that a project does not play its notes with another synthesizer where one is missing), else `Bus` (the same of the instance of its track's effects that hears it), else `Group(g)` (the nearest of the groups it is sent to, going out through their parents, whose effects have one), else `Nobody`. **The first synthesizer of a chain plays the notes of everything that is sent to the chain and none after it** (the one decision of the maintainer: it consumes them); the switch that lets them pass on is 13.5.

**The time of a note** (all integers, in `u128`, and rounded down once). The project runs at `num/den` frames a second; a stretch of the clip covers the source frames `[fs, es)` and the clip itself begins at the source frame `cs <= fs` (a stretch is cut from the clip by a mute, by the start of the plan, or both); the effective speed is `N`. Write `B(f) = f * den * 1_000_000` and compare a time `t` in microseconds as `t * num` with it.
* A note that **starts** before the clip (`t_s * num < B(cs)`) is not played. One that starts in the clip and before the stretch (`B(cs) <= t_s * num < B(fs)`) **and is still sounding where the stretch begins** (`t_e * num > B(fs)`) is **chased**: it begins at sample 0 of the stretch, as hard as it was. One that starts in `[B(fs), B(es))` begins at sample `floor((t_s * num - B(fs)) * 48000 / (num * 1_000_000 * N))`. A note that starts at or after `B(es)` is not in the stretch.
* It ends at `floor((t_e * num - B(fs)) * 48000 / (num * 1_000_000 * N))`, **but not after `limit = floor((es - fs) * den * 48000 / (num * N))`** (a note that goes on past the stretch gets its note off there), and **no sooner than a sample after it begins** (a note of no length is one sample long, so that its note off never comes before its note on).
* A controller or the pitch wheel (an event) is where its time says if it is in the stretch; of those before the stretch and in the clip, **the last of each channel and controller (or of the wheel) is given at sample 0** (the pedal and the wheel are where they were); and **at the end of the stretch (sample `limit`) a pedal (controller 64) that is down is let up and a wheel that is bent is made 8192**, so that the next clip on the same synthesizer does not begin with a pedal that is down.

**The engine** gets all of that in `SoundClipToExport::music` and does nothing about time that the plan has not done: it makes **a silent feed** for such a clip (and the look-ahead does not start a process for it), gives the clip its chain as for any clip, and for each who-plays-them (a clip's own chain, a bus, a group) keeps **one list of events in samples counted from the start of the sound**, sorted by time, with **the note offs before the controllers before the note ons at one sample** (a note off and the note on of the same key at one sample: the off comes first), each note with a number of its own that its note off gives again. Where a chain is made (the clip's, the bus's, the group's: for the first time when the first of what it hears is heard, and for each block) the notes of the block are given to **the first processor of the chain that plays notes** (`BlockProcessor::plays_notes`: a synthesizer; and a stand-in for a synthesizer that is not installed or could not be run, which plays nothing and takes the notes, so that "the first synthesizer" is the same in the plan and in the engine).

**Latency.** A chain whose effects delay the sound is given its input *ahead* (as phase 12 does) so that what comes out is where it is. A synthesizer that has effects before it that delay the sound would be early by what they delay, and one that has effects after it is late by what they delay, unless its notes are asked for at the right time. The rule: with `L_before` the sum of the latencies of the processors before the synthesizer, **the notes it is given in a call are those that the sound of the chain's input window has `L_before` samples earlier** (the window for the sound begins at `s`: the notes' begins at `s - L_before`, which may be before 0 and then has no notes in its first samples). This holds for the first call that makes up for the latency, and for each block, in a clip's chain, a bus and a group, which are all given sound ahead in the same way.

**Seek and lead-in.** A seek makes a new graph, with new instances. The plan begins up to ten seconds before the place the sound is wanted from (phase 12, 12.2d) and the notes in that lead-in are played and not heard; a note that began before the plan did and is still sounding when it begins is chased (above), so one that is held longer than the lead-in is started at its start. A pad that is held across a muted stretch is started again where the mute ends (the same rule).

**Not done in this piece** (and said so in the report): the switch that lets notes pass on (13.5); that the picture of the timeline says that a MIDI clip has no synthesizer on its road (13.6); the tail policies' routes of what a synthesizer rings on after its notes beyond what a clip's ring already has (they are the same as for any effect: a synthesizer is an effect whose tail is its plugin's); notes with several note ports; `PerTrackWithWindows` windows are not looked at for notes (the one instance of the track's effects plays the notes of the whole track).
